# Deployment profiles

A deployment profile is one YAML file, `profiles/<name>.yaml`, that says which features a PingFederate built from
this repository runs and how. Two things follow from it and have to agree: PingFederate's own configuration (OAuth
server settings, access token manager, clients, the CIBA authenticator), which
[deploy/terraform/agentic-idp](../../deploy/terraform/agentic-idp/) applies, and the modules' `OIDF_*` settings,
which the deployment's environment carries. `tools/profile.py` turns the profile into both, checks them, and authors
the config archive the image boots from.

This is not the production profile. `OIDF_DEPLOYMENT_PROFILE`, which a deployment profile's `deployment.mode` sets,
is what [deployment-profile.md](deployment-profile.md) describes: what production refuses at runtime.

The reference part of this page, from [Reference](#reference) on, is generated by `tools/profile-reference.py` from
the presets, the schema, the Terraform modules and the CLI, and the Build workflow's lint job fails when it is not
current. The rest is written by hand.

## What a profile holds

[tools/profile/schema.json](../../tools/profile/schema.json) is the schema; `check` validates a profile against it
after its `extends` chain is merged. The top-level blocks:

| Block | Required | What it says |
|---|---|---|
| `profile` | yes | The profile's name, which must be its file name |
| `description` | no | One line, shown in the presets table below |
| `extends` | no | The preset (or any profile in the same directory) this one is laid over |
| `pf` | yes | PingFederate itself: `base_url` (the origin it advertises, baked into the archive), `naming`, `client_storage` (`xml` or `jdbc`), `scopes`, `user_token_mapping`, `openid_connect`, `extended_properties`, `postgres`, `smoke_client` |
| `deployment` | yes | `mode` (`development` or `production`) and `accepted_risks`, which become `OIDF_DEPLOYMENT_PROFILE` and `OIDF_ACCEPTED_RISKS` |
| `features` | yes | `fapi2`, `attestation`, `federation`, `ciba`, `ssf`, `rar`, `grant_management`: a feature left out is off, and its component switch is set `false` |
| `material` | no | Where `author` finds what the profile does not carry: the runtime TLS p12, trusted CAs, a `KEY=VALUE` secrets file, the conformance clients' JWKS and a `config-store/` overlay, by file name |
| `conformance` | no | The conformance suites' clients, test user and login form; a test rig only, and `check` refuses it in production |
| `env` | no | Settings laid over everything the features imply, last: a string sets one, `null` leaves it unset, and `{{PF_BASE_URL}}` is filled in |

A profile names no secret. The secrets (passwords, client secrets, the runtime TLS p12's password) reach `author`
from the file `material.secrets` names, or `--secrets`, and never reach a rendered file.

## Render, check, author, boot

`tools/profile.py` needs Python 3 and PyYAML, hash-pinned in `tools/profile/requirements.txt`
(`python3 -m pip install --require-hashes -r tools/profile/requirements.txt`), and `terraform` on `PATH` for
anything but `--no-terraform`. A profile is named by path, or by name for one under `profiles/`.

1. **Render.** `python3 tools/profile.py render <profile>` writes, into `.local/<name>/` (or `--out`):
   `terraform.tfvars.json`, the Terraform root's inputs; `vars.env`, the deployment's environment; and
   `stage-profile`, the `stage-modules.sh --profile` the image needs (`conformance` when the CIBA simulator is on,
   else `production`). The environment is the root's `env` output, planned offline against no PingFederate (empty
   state, `-refresh=false`, stand-ins for the material), then the settings that have no PingFederate object, then
   the profile's `env` block.
2. **Check.** `python3 tools/profile.py check <profile>...` validates the schema, the combination rules, the
   settings catalogues, the PingFederate version and the Terraform root's own validations, and names every problem
   it finds. In the public tree it leaves out the catalogue and version checks, which need this repository's
   reactor.
3. **Author.** `python3 tools/profile.py author <profile>` starts a fresh, local PingFederate from the pinned image,
   applies the root to it with fresh state, exports the config archive, checks the archive holds what the
   profile's features need, and with `--age-recipient` encrypts it and deletes the plaintext. It needs Docker,
   Terraform and your Ping Identity licence details (`~/.pingidentity/config`, or `PING_DEVOPS_CONFIG`).
4. **Boot.** The image imports the archive (`data.zip`, or `data.zip.age`) at start, and runs with the settings
   `vars.env` holds in its environment, plus the secrets and the settings that are the node's own. A change made in the admin console
   is gone at the next start: change the profile and author again.

The conformance rig and the reference stacks are built this way. `conformance/up.sh` authors
`profiles/conformance-<PF_PROFILE>.yaml`, and `reference/{single,cluster}/up.sh` author `minimal`, the cluster with
`--set pf.client_storage=jdbc`.

## What check refuses

`check` exits 1 naming each problem. Beyond the schema, it refuses:

- **Features that need each other.** Federation or attestation without `pf.extended_properties: true`
  (PingFederate drops an extended property it has not declared); `client_storage: jdbc` without `pf.postgres`;
  `ciba.authenticator: custom` without its `custom` block; the SSF `emitter` without the transmitter's
  PingFederate objects; an evidence type without the fields the [evidence table](#evidence-types) names, or with
  the attester (`attestation.issuer`) off; `rar` or `grant_management` switched on, which have no Terraform module
  yet.
- **Settings that work against each other.** PingFederate's DPoP nonce requirement (`fapi2.dpop_require_nonce`)
  while the attestation token-endpoint filter is on (`attestation.auth`, on by default): each issues a nonce the
  other refuses, so an RFC 9449 client loops and never gets a token (F-0732). The filter issues combined mode's
  nonce; leave PingFederate's off.
- **What production refuses.** Under `deployment.mode: production`: the CIBA simulator (an approval oracle anyone
  holding an `auth_req_id` can answer); federation with no trust anchor (`self_anchor` or `trust_anchors`); a
  `conformance` block; and every rule of the settings catalogues, judged as the modules judge them at runtime - a
  forbidden value, a risky value whose risk `accepted_risks` does not list (or lists without the expiry a dated
  risk needs), and a required-in-production setting left unset while its component runs.
- **Settings no catalogue declares.** Every `OIDF_*` name the profile generates, its `env` block included, must be
  one a settings catalogue declares; a removed name is refused with its replacement. The catalogues are in
  [docs/configuration](../configuration/README.md).
- **The PingFederate version and the root's validations.** The pinned image must match the Terraform provider's
  product version, and a combination the root's variable validations refuse fails the plan.

## Writing your own profile

Start from the preset nearest what you run and extend it, so a change to the preset reaches you:

```yaml
profile: acme-idp
description: Acme's agentic IdP
extends: federated-agents
pf:
  base_url: https://idp.acme.example
  naming: { id: acmeIdp, display: Acme IdP }
features:
  attestation:
    evidence: [eks, gke]
    aws: { eks_issuers: [https://oidc.eks.eu-west-1.amazonaws.com/id/EXAMPLE] }
    gcp:
      gke_issuers: [https://container.googleapis.com/v1/projects/acme/locations/europe-west2/clusters/agents]
      projects: [acme]
  federation:
    trust_anchors:
      - entity_id: https://trust-anchor.acme.example
        # jwks: the anchor's public keys, pinned (OIDF_FEDERATION_TRUST_ANCHOR_JWKS)
```

`extends` merges mappings key by key and replaces anything else, lists included: the `evidence` list above replaces
the preset's. Two more ways to lay values over a profile, without a new file:

- `--set path=value` lays one value (read as YAML) over the merged profile, as the cluster's
  `minimal --set pf.client_storage=jdbc` does. Under `env` the value is the setting's text as written, and an empty
  value unsets it.
- `--with <profile>` lays another profile's own content over this one, without that profile's `extends` chain, as
  the rig's `PF_HARNESS=1` adds `conformance-federation-harness` to whichever federation profile it runs.

Run `check` on the result before you author it. A setting a feature does not expose goes in the `env` block, and
`check` holds it to the catalogues like any other.
