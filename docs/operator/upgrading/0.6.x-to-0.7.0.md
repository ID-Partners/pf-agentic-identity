# Upgrading from v0.6.x to v0.7.0

For whoever runs a PingFederate built from this repository's artefacts and is on v0.6.0 or v0.6.1 (v0.6.1 changed no
module's behaviour, so the two upgrade the same way). v0.7.0 is Phase 4 of the production programme: durable,
clustered and rotatable. [The release notes](../../releases/0.7.0.md) say what changed, package by package, and number
every "Before you deploy" item in package order; this page puts those items in the order to do them, says what to
check after the first boot, how clustering and key rotation work now, what a rollback can and cannot do, and what each
consumer of this repository changes. The notes' own first item, **Follow the upgrade guide, which puts these items in
the order to do them.**, points here.

PingFederate does not move: v0.7.0 is built and tested against 13.1.3, the image `build/pf-version.env` records, as
v0.6.x was.

**What stops a deployment, above all, is the database.** v0.7.0 creates and alters no table. Each store checks its
migration family at start-up, and a database behind the release is `FAILED_CONFIG`, which the supervisor does not
retry. So the database is migrated before the first v0.7.0 node starts, and the order below starts there.

## Before anything: the preflight

Take `oidf-preflight.jar`, `oidf-db-migrate.jar` and `SHA256SUMS` from the assets of the v0.7.0 release, check them,
and run the preflight on each environment's settings, naming the process the file is for:

```sh
sha256sum --ignore-missing -c SHA256SUMS      # in the directory holding the downloaded assets
java -jar oidf-preflight.jar --process pingfederate --env-file <your env file> --profile production
java -jar oidf-preflight.jar --process pingfederate --format docker --env-file <a docker env file> --profile production
```

v0.7.0's jar judges more than v0.6.x's did (**Run the preflight again, naming the process.**): besides what the
start-up sweep refuses, it reports as `REFUSED (at read):` what a component refuses when it reads a setting - a removed
name such as `OIDF_SSF_PUSH_RETRY_MAX_ATTEMPTS`, a number or a switch that does not parse, a secret set beside its
`_FILE` variant. `--format docker` reads the file as `docker run --env-file` does, so drop a `sed` that quoted every
value. Exit 0 is clean, 1 names each refusal and its fix, 2 is a file or an argument it could not read
([preflight.md](../preflight.md)). It cannot see the database, PingFederate's own configuration or the topology a
node will report.

## The database, first

Do this before any v0.7.0 PingFederate starts, against each database a store uses: the authority's (hosted entities,
Trust Marks, key history, and now key observations and pinned subordinates), the agent registry's, the SSF `tables`
store's, and, for a cluster, the lease data store's. [database-migrations.md](../database-migrations.md) is the
reference; this is the order.

1. **Take a backup.** The migrations are forward-only (below, "Rollback to v0.6.x"); a backup taken now is the only way
   back to a v0.6.x schema.
2. **Create the two roles** if you do not have them: a migrator that owns the tables, and PingFederate's runtime role
   with rows only ([Roles](../database-migrations.md#roles)). On v0.6.x PingFederate's data store role usually created
   the SSF tables, and whoever applied the federation SQL owns those.
3. **Hand the v0.6.x tables to the migrator**, as a superuser, for the tables the database has: `ALTER TABLE <table>
   OWNER TO oidf_migrator;` for `ssf_streams`, `ssf_stream_subjects`, `ssf_pending_sets`, `ssf_scim_users`,
   `hosted_entity`, `hosted_entity_audit_log`, `trust_mark_grant`, `trust_mark_audit_log`, `federation_key_current`,
   `federation_key_history` and `agent_identity`. Without it `migrate` stops at V302 with `must be owner of table
   ssf_streams`, rolled back. Then take `CREATE` away from PingFederate's role, which v0.6.x needed and v0.7.0 does not (`REVOKE CREATE ON SCHEMA public FROM <its role>;` and the same `ON DATABASE`): the runtime role must own nothing and create nothing. This takes DDL away from a v0.6.x node, which runs it at every start, so move every node to v0.7.0 straight after.
4. **Look for duplicate userNames** in the SSF database before V310 (**Look for duplicate userNames before the
   upgrade.**):
   `SELECT lower(user_name), array_agg(subject_key) FROM ssf_scim_users WHERE user_name IS NOT NULL GROUP BY 1 HAVING count(*) > 1;`
   Rename one of each pair now, or let the first start key one and report the rest.
5. **Adopt each family the database already has**, as the migrator, at the version v0.6.x left it at (**Run
   `oidf-db-migrate.jar` before you start 0.7.0 PingFederate.**):

   ```sh
   export OIDF_DB_MIGRATE_JDBC_URL='jdbc:postgresql://db.example.com:5432/oidf?sslmode=verify-full'
   export OIDF_DB_MIGRATE_USER=oidf_migrator OIDF_DB_MIGRATE_PASSWORD_FILE=/run/secrets/oidf_migrator
   java -jar oidf-db-migrate.jar adopt --family federation --baseline 103   # the authority's tables are there
   java -jar oidf-db-migrate.jar adopt --family agent --baseline 200        # agent_identity is there
   java -jar oidf-db-migrate.jar adopt --family ssf --baseline 301          # SSF ran with storeDialect=tables
   ```

   adopt compares the live tables with what the scripts up to the baseline build, column order aside, and records
   nothing unless they match. Skip a family the database does not have.
6. **Migrate every family**, which applies what each lacks: platform V10 (the lease table), federation V104-V106, and
   SSF V302-V310, and creates any family the database did not have:

   ```sh
   java -jar oidf-db-migrate.jar migrate
   ```

   This is every migration item of the notes at once: **Apply SSF migrations V303-V305, then the grants again.**,
   **Apply SSF migration V306 before PingFederate starts 0.7.0, then the grants again.**, **Apply SSF migration V307,
   then run `grants` again, before the new jar starts.**, **Apply SSF migration V308 before the new jar starts.**,
   **Apply SSF migration V309, then run `grants` again, before the new jar starts.**, **Apply SSF migration V310, then
   run `grants` again, before the new jar starts.**, **Apply V104 before you start the new release.**, **Migrate the
   authority's database to V105 before using the database store.**, **Migrate the authority's database to V106
   first.** and, for a cluster, the V10 half of **Clustered nodes need V10 and `OIDF_LEASE_BACKEND=jdbc`.**
7. **Grant the runtime role its rows**, after the migrate, since V304, V306, V307, V309 and V310 add tables or
   sequences, and the start-up check reads `oidf_schema_history` as that role (**Rerun `grants` before the new
   PingFederate starts.**):

   ```sh
   java -jar oidf-db-migrate.jar grants --runtime-role pf_runtime --apply
   java -jar oidf-db-migrate.jar validate
   ```

   A database that holds only some families takes one `grants --family` run for each.
8. **Then start PingFederate** (**Migrate first, then start PingFederate; restart it after a late migrate.**). A node
   that started before the migrate stays `FAILED_CONFIG` until it is restarted.

An SSF store on the `ldm` dialect has no `ssf` family. Its database is the Identity Object Model's, and the start-up
check reads that model's own ledger, `idm.schema_migration`, instead: grant PingFederate's role `SELECT` on it and
`USAGE` on schema `idm` (**Grant `SELECT` on `idm.schema_migration` for an `ldm` SSF store.**), and on a directory
built outside the model repository's migrations, record by name what is already there before the upgrade (**An
Identity Object Model database not built through the model repository's migrations has an empty ledger.**,
[The Identity Object Model's ledger](../database-migrations.md#the-identity-object-models-ledger)).

While you are at the database: each data store's JDBC URL should carry the driver's timeouts and
`sslmode=verify-full`, and the runtime role a `statement_timeout` (**Set the driver's timeouts and
`sslmode=verify-full` on each data store's JDBC URL.**, [database.md](../database.md)); a store statement now has a
10-second deadline (**Expect a statement that runs longer than 10 seconds to fail.**); and a direct JDBC URL is refused
in code under production (**Keep direct JDBC URLs off production.**). The image now carries PgJDBC 42.7.13: remove a
driver you added yourself (**Remove a PostgreSQL driver you added to the image yourself.**).

## Before you deploy - the checklist

Every numbered item of the notes, by its bold title, in the order to do them. The database's items are above; each
group below says which items it holds.

### 1. The topology

Every node now reads what it is (**Say what each node is, if PingFederate does not.**): `OIDF_CLUSTER_MODE`, else
PingFederate's `pf.operational.mode`. A standalone PingFederate whose `run.properties` says `STANDALONE` (the image's
default) needs nothing; a blank, unusual or disagreeing mode is an unknown topology, which production refuses for
every component. A clustered node refuses every store kept in memory (**Do not run a clustered node on
`in-memory-state`.**). The rest of a cluster's needs are under "Clustering" below.

### 2. Removed and stricter settings

- **Unset the signingAlgorithm init-params.** - set `OIDF_FEDERATION_SIGNING_ALG` instead.
- **Unset `OIDF_SSF_PUSH_RETRY_MAX_ATTEMPTS`; `OIDF_SSF_PUSH_PAUSE_AFTER_SECONDS` replaces it.**
- **Check the new bounds before you upgrade.** - `OIDF_SSF_PUSH_RETRY_BACKOFF_SECONDS` 1-60, `OIDF_SSF_POLL_MAX_EVENTS`
  0-1000.
- **List any other transmitter origin your receiver uses.**
- **Give the SSF receiver https URLs in production.** and **Make Kafka buildable, or switch it off.**
- **Read the narrower refusals.** - a governed setting now refuses only the components that read it.
- **Write `OIDF_REGISTERED_CLIENTS_ENABLED` as `true` or `false`.**, **Write `OIDF_EVENTS_AUDIT` as `true` or `false`,
  and `OIDF_EVENTS_MAX_VALUE_LENGTH` as a whole number from 16.**, **Give `OIDF_ATTESTER_FEDERATION_ENTITY` and
  `OIDF_ATTESTER_CIMD_URL` as URLs.** and **Look up `OIDF_AUTHORITY_ADMIN_TOKEN` on its new page.**
- **List the browser origins that read the federation, SSF or CAS metadata documents.** - `*` stops the servlet; a
  `corsAllowOrigin=*` you set must go.
- **Expect IPv6 callers to share an allowance per /64.** - a value of `OIDF_RATE_LIMIT_IPV6_PREFIX` outside 32-128
  stops the challenge endpoints and the attester's servlets.
- **List your load balancer in `OIDF_TRUSTED_PROXIES` if the resolve endpoint is behind one.** and **Set
  `OIDF_TRUSTED_PROXIES` where gm-api sits behind a proxy and has no `grantManagementEndpoint`.**

### 3. Federation keys and subordinates

- **Have a key for the algorithm before you choose ES256 or ES384.**
- **Turn key history on in production.** and, on a cluster, **Turn key history on for a clustered node.**
- **Raise a grace shorter than your longest Trust Mark or registration.** - the defaults (86400) pass.
- **Keep the leases in the authority's database to fence the observer.**
- **Expect signing to lag PingFederate's key change by the delay.** and **Expect registration responses signed with
  OIDF_FEDERATION_SIGNING_ALG.**
- **Pin every subordinate before a production node starts.** - capture the keys on a development node first
  (`tools/pin-subordinates.py capture`), confirm them out of band, then enrol or list them.
- **Expect enrolments and key changes to wait for approval.**, **Agree a rollover overlap with each subordinate.**,
  **Re-pin before a subordinate rolls its keys over.** and, on a cluster, **Use a lease backend that elects across the
  cluster.**
- **Expect the resolve cap to count more.**, **Send signed request objects, or use PAR, for relying parties that
  renew automatically.** and **Apply FAPI 2.0 at device authorization.**
- **Expect 503 from the Trust Mark admin routes without a store.**

### 4. Operator access and the clients you run

- **Update operator clients to answer `use_dpop_nonce`.** - every DPoP-bound operator call now meets a nonce challenge
  first; production refuses `OIDF_OPERATOR_DPOP_NONCE=false`.
- **Set `OIDF_OPERATOR_API_ENABLED=true` in production if the operator API is configured.**
- **Grant `ssf.admin` to the operators who may pause, resume and retry streams.**
- **Stop sending gm-api string-form or malformed `act` claims.** - do not upgrade gm-api where it must accept
  delegated tokens from this platform's token-exchange mapping until U-0009 is settled.
- **Stop sending authorization_details on ID-JAG token exchanges.**
- **Update any client that matches the issuance endpoint's error codes.** and **Check Kubernetes service-account names
  if a cluster uses unusual ones.**

### 5. SSF behaviour

- **Expect 200 and 204 to count as delivered, and a 400 without `invalid_request` to be retried.**, **A push endpoint
  the outbound policy refuses pauses its stream.** and **Watch for dead SETs.**
- **Expect paused streams' queues to grow, and alert on the trim.**, **Know that a disable deletes the queue.** and
  **Check `inactivity_timeout` before upgrading.**
- **Read the bridge's return as "queued", not as a SET count.**, **Expect a SET's streams to be chosen about a second
  later.** and **Size the hand-off for a store outage.**
- **Expect the first boot to start with an empty inbox.** and **Expect the receiver to wait for its JWKS.**
- **Set proxy and receiver timeouts above the long-poll wait.**
- **Expect session-revoked after the confirmation, and none for a declined sign-off.** - a hand-made `web.xml` must
  map `SsfLogoutConfirm` over `*.ping`.
- On a cluster, **A receiver may see a SET twice after a node fails.**

### 6. Metrics, logs and audit

- **Scrape each node, not the load balancer.**, **In production, give Prometheus a key, not a secret.** and **Sum over
  `copy`, or keep it.** ([metrics.md](../metrics.md)).
- **Expect the RAR plugin's and gm-api's lines at their own level.**, **Turn the RAR plugin's summary line back on if
  you read it.**, **Look up a refusal's reference as PingFederate's id.** and **Check a log parser against the new
  suffix.** ([logging.md](../logging.md)).
- **Expect RAR decisions and refused attester clients in the audit log.**
- **Expect the engine's copy to start no background job but its Redis watchdog.**

### 7. Clustering, if you run one

- **Run federation, attestation, automatic registration and the SSF receiver on one node, or test them on your
  cluster yourself.**
- The V10 and lease half of **Clustered nodes need V10 and `OIDF_LEASE_BACKEND=jdbc`.**, and **SSF on a cluster needs
  the `tables` dialect.**
- **Plan on a disabled client working for a minute on the other engines.**, **Have your load balancer follow engines by
  name.** and **Restart a new engine once after its first replication if its outbound calls trust a private CA.**
- **The registration sweeper's first pass now runs at start-up.** and **A Redis password with `+` or a double-escaped
  `%` changes meaning.** apply to a single node too.

### 8. For whoever releases this repository

- **Run the licensed jobs on the commit you tag.** - not a deployment step; it is here so that every item has a place.

## Clustering

From v0.7.0 a cluster is supported in one shape and for some components only
([deployment-limits.md](../deployment-limits.md)): a `CLUSTERED_CONSOLE` and `CLUSTERED_ENGINE` nodes on the
production profile, PingFederate's OAuth clients in a database (JDBC client storage), one Redis for every node,
`OIDF_LEASE_BACKEND=jdbc` with the platform family's V10 in that data store's database, and SSF on the `tables`
dialect. The cluster suite drove PingFederate's clients and tokens, the leases and SSF's transmitter across two
engines; federation, client attestation, automatic registration, the SSF receiver, hosting, the operator APIs and FAPI
are not verified on a cluster (F-0601, high, 0.8.0).

- **Each node's mode.** Set `OIDF_CLUSTER_MODE` on every node to `CLUSTERED_CONSOLE` or `CLUSTERED_ENGINE` (or
  `CLUSTERED_DUAL`), the same as PingFederate's `pf.operational.mode`; disagreeing is an unknown topology, refused in
  production. The start-up audit's `topology` line and `/agentic-identity/info`'s `topology` object say what the node
  read ([clustering.md](../clustering.md#which-topology-a-node-has)). A console node runs no background job.
- **Leases.** `OIDF_LEASE_BACKEND=jdbc` and `OIDF_LEASE_DATA_STORE_ID` on every node, with V10 applied: the
  registration sweeper, the SSF poll receiver, the SSF stream sweeper, the federation key observer and the subordinate
  monitor each run on one node at a time, failing over within the lease's TTL and a tick (40 s at the default
  `OIDF_LEASE_TTL_SECONDS=30`). The `redis` backend can lose a lease in a Redis failover and needs the `redis-lease`
  risk in production ([clustering.md](../clustering.md#leases)).
- **SSF.** On `tables` each push stream is leased to one deliverer (`ssf_stream_lease`), and the receiver's inbox, the
  emission outbox and the logout replay keys are shared; no lease backend setting is needed for it.
- **The `ldm` limit.** The `ldm` dialect keeps its leases, inbox and outbox in each node's memory, so a clustered
  production node refuses SSF on it, naming `OIDF_SSF_STORE_DIALECT=tables`. `ldm` is single-node through 1.0.0: David
  accepted the S10f family (F-0387, F-0535, F-0550, F-0555, F-0560) until 2027-06-30, with target 1.1.0. Stay on one
  node, or move SSF to `tables` before you cluster.
- **Moving a single node to a cluster** is a new deployment of the console and engines on the same databases, not an
  upgrade step: [reference/cluster](../../../demo/reference/cluster/README.md) is the worked example, and
  [clustering.md](../clustering.md#the-reference-cluster) records what PingFederate itself needs (client storage,
  replication, `DNS_PING`).

## Key rotation without a restart

From v0.7.0 the federation follows PingFederate's signing key while it runs (S6A, S6B; F-0011 closed). Change the
active OAuth/OIDC signing key in PingFederate as you normally would - a dynamic key's rotation, or a new static key
through the admin console or `PUT /pf-admin-api/v1/keyPairs/oauthOpenIdConnect` - and:

1. within about 30 seconds the key observer, one node at a time under its
   `federation-key-observer` lease, records the new key in `federation_key_observed` and every node publishes it in the
   Entity Configuration's `jwks`;
2. after `OIDF_FEDERATION_KEY_ACTIVATION_DELAY_SECONDS` (3600) the cluster signs its Entity Configuration, statements,
   Trust Marks, registration responses and SSF SETs with it, as OpenID Federation 1.0 §11.2 orders a rotation; a Trust
   Mark signed with the old key is minted again;
3. the old key stays in `jwks` and `/federation/historical_keys` for `OIDF_FEDERATION_KEY_HISTORY_GRACE_SECONDS`.

No restart is needed at any step. What it needs: key history on (`OIDF_FEDERATION_HISTORICAL_KEYS=true`), an active
key of the algorithm `OIDF_FEDERATION_SIGNING_ALG` names, a grace at least the longest Trust Mark or registration
lifetime, and on a cluster the leases in the authority's database. `OIDF_FEDERATION_KEY_ACTIVATION_DELAY_SECONDS=0`
signs from the observer's next tick, at the cost of peers with a cached Entity Configuration failing until they fetch
it again. `conformance/verify-key-rotation.sh` runs the whole sequence on the rig and prints each step with its time;
the notes' "What we verified" has the release's run.

## After the first boot

1. **The start-up audit** in server.log: a `topology` line with the mode you meant; each JDBC store's schema check
   `CURRENT` for its family (`platform.schema.checked`), with the head the release carries - platform V10, federation
   V106, agent V200, ssf V310; and nothing `REFUSED` or `FAILED_CONFIG` you did not mean
   ([startup-audit.md](../startup-audit.md)).
2. **Ready**: `GET /agentic-identity/health/ready` answers 200 only when every enabled component is `READY` or
   `DEGRADED` ([health.md](../health.md)).
3. **SSF**: `ssf_pending_sets` still holds what v0.6.x had queued, every row with a `seq`; each push stream has an
   `ssf_stream_lease` row (V303 backfilled them); the transmitter's start-up line names its dialect and whether its
   leases are shared. A SCIM `userName` conflict, if any, is reported as `ssf.scim.username_conflict`.
4. **Metrics**: `GET /agentic-identity/metrics` with an operator token holding `oidf.metrics.read` answers the
   Prometheus text format ([metrics.md](../metrics.md)).
5. **Federation**: the Entity Configuration's `jwks` carries the active key, and `federation.key.observed` appears once
   the observer has run.

## Rollback to v0.6.x

The migrations are forward-only: there is no down script, and `oidf-db-migrate.jar` has no command that undoes one.
The clean way back is the backup taken before step 1 of "The database, first", restored with the v0.6.x artefacts or
image and PingFederate's configuration archive from before the upgrade. Anything written after the upgrade is lost
with it. What happens instead if a v0.6.x node is pointed at the migrated database, read in the code (v0.6.1 at
11949951, v0.7.0's code at d9f7892c) and tried on PostgreSQL 16 (the notes' "What we verified"):

- **v0.6.x's start-up DDL fails.** Its `JdbcSsfStore.ensureSchema` runs `CREATE TABLE IF NOT EXISTS` and
  `ALTER TABLE ... ADD COLUMN IF NOT EXISTS` at every start, as PingFederate's role. After step 3 that role owns no
  table and holds no `CREATE`, so the SSF store fails to start until the tables are handed back to it (as a superuser,
  `ALTER TABLE ... OWNER TO` the runtime role) - which undoes the separation of roles.
- **Data v0.6.x does not read.** It ignores the new tables and columns: SETs queued in `ssf_emission_outbox` and not
  yet fanned out are never sent; the receiver's `ssf_receiver_inbox`, `ssf_dead_sets`, `ssf_logout_pending` and
  `ssf_stream_lease` are not used; a stream an operator paused (`paused_by`) can be resumed by its receiver; the
  federation's observed keys (V104) and pinned subordinates (V105, V106) are not used, so subordinates are served with
  their live keys again (F-0012's exposure back); `oidf_lease` and `oidf_schema_history` are unused. Rows v0.6.x writes
  take the new columns' defaults or nulls: a pending SET's `seq` comes from its sequence (the runtime role holds
  `USAGE` on it), and V310's unique key on `user_name_key` admits the nulls v0.6.x leaves.
- **Going forward again.** A v0.7.0 node started after such a rollback finds the families current (nothing to migrate)
  and backfills what v0.6.x left: an `ssf_stream_lease` row for a push stream created meanwhile, the SCIM keys of new
  users.
- **Settings v0.6.x needs back.** The `signingAlgorithm` init-params if you had set them, and
  `OIDF_SSF_PUSH_RETRY_MAX_ATTEMPTS` if you relied on the five-failure pause. v0.7.0's new names
  (`OIDF_CLUSTER_MODE`, `OIDF_LEASE_*`, `OIDF_METRICS_*`, the new SSF and federation settings) can stay: v0.6.x lists
  unknown `OIDF_` names under development and, under production, refuses the components of their family - so remove
  them on a production rollback, or run the v0.6.x preflight against the file first.
- **Clients.** An operator client that answers DPoP nonces works with v0.6.x, which sends none. A Prometheus scrape
  with an unbound token is refused by v0.6.x in production, which has no metrics route at all.

### pf-oidf-modules

Read at `55629cc` (main, 2026-09-24).
