# Upgrading from v0.7.0 to v0.8.0

For whoever runs a PingFederate built from this repository's artefacts and is on v0.7.0. v0.8.0 is Phase 5 of the
production programme: client attestation complete against ABCA draft-11. [The release notes](../../releases/0.8.0.md)
say what changed, package by package, and number every "Before you deploy" item in package order; this page puts
those items in the order to do them, then walks through the four changes that need the most work (CIMD, required
claims, external ceilings and SPIRE), what to check after the first boot, and what a rollback can and cannot do. The
notes' own first item, **Follow the upgrade guide, which puts these items in the order to do them.**, points here.

PingFederate does not move: v0.8.0 is built and tested against 13.1.3, the image `build/pf-version.env` records, as
v0.7.0 was.

**What stops a deployment** is, in order: a database behind the release (three new migrations, below); a removed
setting still set (`OIDF_ATTESTER_CIMD_URL`, `OIDF_ATTESTER_SPIRE_ENTRIES_URL`, the `clientAttestationPopMethodsSupported`
init-param), each refused by name; what production now refuses (inline attester keys, static wallet provider keys,
external clients without `OIDF_ATTESTER_EXTERNAL_CEILINGS`, Entra directory entries without a tenant); and two checks
that are on by default, refresh-token binding and the revocation check once a register is configured.

## Before anything: the preflight

Take `oidf-preflight.jar`, `oidf-db-migrate.jar` and `SHA256SUMS` from the assets of the v0.8.0 release, check them,
and run the preflight on each environment's settings, naming the process the file is for:

```sh
sha256sum --ignore-missing -c SHA256SUMS      # in the directory holding the downloaded assets
java -jar oidf-preflight.jar --process pingfederate --env-file <your env file> --profile production
```

v0.8.0's jar knows the removed names and prints each as `REFUSED (at read)` with the setting that replaces it, or as
`not refused (switched off)` while its component is off; it knows every new setting's choices and bounds. Exit 0 is
clean, 1 names each refusal and its fix, 2 is a file or an argument it could not read ([preflight.md](../preflight.md)).
It cannot see the database, PingFederate's own configuration (extended properties, init-params in `web.xml`) or what
your clients send.

## The database, first

Do this before any v0.8.0 PingFederate starts. v0.8.0 adds three migrations, all additive:

| Family | Migration | What it does | Needed when |
|---|---|---|---|
| `federation` | V107 | `hosted_entity.federation_jwks` and `entity_configuration`, and a check that a self-signed entity has keys and no hosting key reference | you run the authority on a database (**Migrate the federation family to V107 first.**, L01B) |
| `agent` | V201 | each agent's status (`active` for every existing row), reason, time, actor and row version, and `agent_status_audit_log` | you keep the agent registry in PostgreSQL (**Run `db-migrate migrate --family agent` and `grants` before deploying if you keep a registry.**, A22) |
| `agent` | V202 | `agent_identity.status_idx`, each agent's entry in the attester's status list, backfilled at random | as V201 (**Run the agent family's migrations first.**, E12) |

1. **Take a backup.** The migrations are forward-only (below, "Rollback to v0.7.0").
2. **Migrate**, as the migrator role, then **grant** the runtime role its rows, since V201 adds a table:

   ```sh
   java -jar oidf-db-migrate.jar migrate
   java -jar oidf-db-migrate.jar grants --runtime-role pf_runtime --apply
   java -jar oidf-db-migrate.jar validate
   ```

   `migrate` with no `--family` also creates any family the database does not have. To migrate only what a database
   holds, run `migrate --family federation` or `migrate --family agent` and one `grants --family` for each; the agent
   family is needed only if the registry is in PostgreSQL (`OIDF_AGENT_REGISTRY_MODE=database`).
3. **Then start PingFederate.** A store whose family is behind the release is `FAILED_CONFIG` at start-up and is not
   retried; restart a node that started before the migrate. During a rolling upgrade a v0.7.0 node still running
   inserts agents without a `status_idx`; v0.8.0 gives such an agent its index when it next attests it.

## Before you deploy - the checklist

Every numbered item of the notes, by its bold title, in the order to do them. The database's items are above; each
group says which items it holds. Four groups have their own section further down.

### 1. Removed settings and init-params

- CIMD: **`OIDF_ATTESTER_CIMD_URL` is removed.**, **Convert with `tools/cimd-split.py`.**, **CIMD client ids become
  their URLs.** (B02B) and **Move a CIMD document to OIDF_CIMD_CLIENTS before upgrading.**, **Take trust roots, issuers
  and keys out of CIMD documents.**, **Keep each CIMD document under 5 KiB, or raise the cap.**, **Serve each document
  from a public https address.** (B02A) - see [CIMD](#cimd) below.
- SPIRE: **Unset `OIDF_ATTESTER_SPIRE_ENTRIES_URL` before you upgrade.**, **Deploy the SPIRE entry reader and set the
  reader settings to keep SPIRE selectors.**, **Create the PingFederate SSL client key pair and give its public key to
  the reader.**, **Move any policy off `workload.attributes.selectors` and `.spire`.** and **Choose the failure mode.**
  (B08) - see [SPIRE](#spire) below.
- **Remove `clientAttestationPopMethodsSupported` from the federation servlet's init-params.** (E05): the federation
  servlet does not start while it is set.
- **Configure the GM PDP and audience.** (REVIEWCFG): gm-api's deployment descriptor no longer carries defaults for them.

### 2. What production now refuses

- Attester keys (B04): **Move inline attester keys to OpenBao.**, **List your transit keys in
  `OIDF_ATTESTER_SIGNING_KEYS` with the issuers they sign for.**, **Set `OIDF_ATTESTER_SIGNING_KEY_REF` for federation
  clients.**, **Federation entries may no longer name a signing key.**, **Give the attester's OpenBao token a policy
  limited to its own keys.** and **Do not rotate a federation-published attester key in place.**
- Wallets (B05): **Pin every wallet client's provider.**, **Publish wallet provider keys in
  `openid_wallet_provider.jwks`.**, **Check your wallets' `typ`.**, **Move off `OIDF_WALLET_PROVIDER_JWKS` in
  production.** and **Expect new wallet `agent_id`s.**
- External clients (B03): **Set `OIDF_ATTESTER_EXTERNAL_CEILINGS` if you run a federation entity or CIMD clients in
  production.** and **Merge a client's federation instances under one `client_id`.** - see [External
  ceilings](#external-ceilings) below.
- The asserted context (B10A): **Send `asserted_context` on every request to a client that names a resolver.**, **Stop
  sending `asserted_context` to clients that name no resolver.**, **Give every `OIDF_ENTRA_AGENT_DIRECTORY` entry a
  `tenant` and `instances` in production.** and **Check PingFederate clients that already had
  `attestation_asserted_context_resolver` set.**

### 3. On by default: refresh-token binding and the revocation check

Refresh-token binding (E15) is `on` unless you turn it off: a refresh token issued to an attested request is bound to
the client instance key. **Expect another instance's refresh to fail.**, **Expect bound tokens to need an
attestation.**, **Use Redis on a cluster, and keep its keys from being evicted.**, **Plan for 503 when Redis is
down.**, **Keep bindings at least as long as the refresh tokens.**, **Keep rotated-out tokens bound through
PingFederate's grace period.**, **Know that only the token-endpoint filter binds.**, **Declare the new extended
property.** (`attestation_refresh_binding`), then later **Turn on `strict` only after the old tokens are gone.**; or
**Accept the risk to turn it off.** (`refresh-binding-off`).

The revocation check (E11) runs once a register is configured (`OIDF_CLIENT_REVOCATION_MODE` unset is `live` then):
**Expect suspended and revoked agents to be refused at the token endpoint once the agent registry is on.**, **Know
which requests the check covers.**, **Name the device-instance registry to check device instances.**, **Plan for 503
when a register is down.**, **Turn the check off, or install the filter, in a deployment without the token-endpoint
filter.**, **Revoking does not withdraw tokens already issued.** and **Grant the new operator scopes only to operator
clients.**

### 4. Callers that must change

- Grant Management: **Use unbound bearer access tokens for GM.** (REVIEWGM).
- Every inbound endpoint: **Keep request bodies within 1 MiB.** (REVIEWHTTP).
- Device enrolment and iOS clients: **Make sure every iOS client sends the bound nonce.**, **Expect stale sign-ins to
  be refused at first enrolment.** (REVIEWENROL) and **Send bounded enrolment proofs.** (REVIEWPROOF).
- Token issuers and clients: **Check that your token issuers' and clients' clocks are within a minute of yours.**
  (REVIEWPINGONE).
- Attesting clients: **Check your required-claim names.** and **Clients that branch on `invalid_client`.** (E03) - see
  [Required claims](#required-claims-and-the-attestation-error-code) below; **Check combined-mode clients for
  `use_attestation_challenge`.** and **Review the challenge cap if refusals are frequent.** (E02); **Keep
  PingFederate's DPoP nonce requirement off with attestation combined mode.** (E02B) and **Turn off
  `fapi2.dpop_require_nonce` in a profile that also runs the attestation filter.** (F0732).
- Attester metadata: **Check any algorithm list you set on the federation servlet.**, **If you set
  `attestationSigningAlgValuesSupported`, make it name your attester keys' algorithms, on the issuance servlet.**,
  **Expect 404 from `/federation/attestation-challenge` if you set `attestationChallengeEndpointEnabled=false`.** and
  **Expect no attestation members while `ATTESTATION_AUTH` is not serving.** (E05); **Check `challengeEndpointEnabled`
  before you rely on the attester's challenge endpoint.** and **Set `challengeEndpointEnabled=false` on the issuance
  servlet if you set it on the metadata servlet alone.** (B11A).
- Trust bundles: **Make sure every `attestation_bundle_url` is reachable from PingFederate.** (REVIEWJWKS).

### 5. Features you turn on

Each is off until you set it; the items say what to do first.

- The agent registry (A22): **The agent registry is off unless `OIDF_AGENT_REGISTRY_MODE` is set.**, **A storage fault
  is now 503, not 500.** and **A new operator surface, /federation/attestation/agents.**
- Wallet status lists (B06): **Open egress from the attester to your wallet providers' status list hosts.**, **Expect
  503 while a status list is unreachable.**, **Decide which wallet providers must carry `status`.** and **Review the new
  size settings.**
- Single use (E06): **Declare `attestation_single_use` before setting it.** and **Raise the attester's issuance limit
  before turning single use on.**
- Trust Marks (E07): **Declare `attestation_required_trust_marks` before setting it.** and **Check that your attesters
  carry the marks before you require them.**
- Key-storage and user-authentication minimums (E08): **Declare the two extended properties before setting them.** and
  **Check what your attesters assert before setting a minimum.** A minimum refuses every workload client, because the
  workload attester asserts neither claim.
- Status lists for client revocation (E12): **Turn the lists on before the verifier mode.**, **Make the list URL
  reachable from every verifier.**, **Give the attester's list a governed signing key.** and **Expect a status-list
  revocation to arrive late.**
- Outbound CAEP (E13): **Decide whether to turn it on.**, **Run the transmitter beside the registers.**, **Make
  receivers hear the subject.**, **Give peers one identifier for both roles.** and **Watch for unsent SETs.**
- SCIM agent instances (E14): **Grant `oidf.admin.scim` to provisioning clients only.**
- Federation (L01A, L01B): **Give your policy engine a policy for the new action names before you list them.**,
  **Declare the two per-client properties in PingFederate before you set them.**, **Expect a renewal to keep what you
  set on a federation client.**, **Leave consuming historical keys off unless you need it.**, **Expect self-signed
  agents to work on a database.** and **Send `federation_jwks` to re-key a self-signed agent.**
- The device directory (TAIL5): **Record or apply the model's ledger rows before the datasource plugin or
  device-enrolment reads the directory.** and **Check the transmitter's clock if you receive device-compliance-change
  SETs.**

### 6. Clustering

**Run federation, attestation, automatic registration and the SSF receiver on one node, or test them on your cluster
yourself.** 0.8.0 makes 0.7.0's clustering claim and no wider one (F-0601,
[deployment-limits.md](../deployment-limits.md)). If you run a cluster anyway, refresh-token binding needs Redis
(above).

### 7. For whoever builds or extends this repository

**Install PyYAML before running `tools/profile.py`.**, **Name a conformance profile with `PF_PROFILE`.** and **Move
Terraform you applied from `conformance/terraform` or `reference/terraform`.** (AGENTIC-IDP-PROFILES), and
**Extension authors: `StatusListClient` moved.** (E12).

## CIMD

**Who this is for.** Anyone who sets `OIDF_ATTESTER_CIMD_URL` (or the system property `oidf.attester.cimd.url`). Only
the development profile has honoured it since 0.4.0, and B02A made it build nothing. From 0.8.0 it is a removed name:
set to anything not blank, the attester's settings catalogue refuses it on its first read, in every profile, with
`OIDF_ATTESTER_CIMD_URL was removed in 0.8.0; set OIDF_CIMD_CLIENTS instead`. Unless
`OIDF_ATTESTATION_ISSUER_ENABLED=false`, the attester starts (switched on, or inferred when none of its settings is
set, as with only this variable), so it is `FAILED_CONFIG` (`/federation/attestation` answers 503) and
`oidf-preflight.jar` prints the same line as `REFUSED (at read)`. With the switch `false`, preflight shows the line as
`not refused (switched off)`, and it is refused the moment you switch the attester on. If you never set it, there is
nothing to do here.

The old variable named one document whose `spiffe_mappings` gave every client its SPIFFE ids, its issuer and its
trust roots, and anyone who could change that document could hand the attester a trust root (F-0067). The 0.8.0
shape splits it: the operator lists each client in `OIDF_CIMD_CLIENTS` with its issuer, evidence type, trust root and
subject prefixes, puts the trust roots in `OIDF_CIMD_TRUST_BUNDLES`, and each client publishes one Client ID Metadata
Document at its own URL that lists only its instances and their ceilings (CAS §6.1). The
attester README describes both settings.

**The client id becomes the URL.** Under CIMD a client's id is the URL its document is served at (CAS §6.2,
CIMD draft -02 §3), so converting renames every CIMD client: `demo-attest-railway` becomes, say,
`https://agents.example.com/clients/demo-attest-railway`. PingFederate, the attestation's `sub` and the bridge keys
all use the new id.

### Steps

1. **Convert the old document.** Download it once, then run the converter on the file (it never fetches anything):

   ```
   python3 tools/cimd-split.py --in old-cimd.json --out-dir cimd/ \
       --url-template 'https://agents.example.com/clients/{client_id}'
   ```

   `--map renames.txt` (lines of `old_client_id=https://new/url`) names a client's URL by hand; a client it leaves
   out takes the template. The converter writes one document per client, `oidf-cimd-clients.json` and
   `oidf-cimd-trust-bundles.json`, and prints the rename table. It stops, writing nothing, on an entry that carries
   `signing_jwk` (move that key to OpenBao and name it with `signing_key_ref`), on a client whose entries name
   different issuers, evidence types, trust roots or signing keys, and on a URL the CIMD rules refuse. The converter is
   in this repository, not in the public release; ask for it if you deploy from the public repository.
2. **Review the trust roots.** They came from an unsigned document, so the first run writes them as
   `"jwks": "REVIEW"` and exits 3, printing each key's RFC 7638 thumbprint and each `jwks_uri`. Confirm each with the
   trust domain's owner by a channel other than the old document, then run again with `--accept-bundles` (or fill
   them in by hand).
3. **Review the subject prefixes.** Each client's `subject_prefixes` is the longest common prefix of its SPIFFE ids,
   cut back to the last `/`. A document can list only subjects under it, so narrow it if it admits more than the
   client should have.
4. **Publish each document at its URL.** Over https, from a public address (the fetch has no exemption from the
   outbound rules in production), with a JSON content type, no redirect, and under 5 KiB unless you raise
   `OIDF_CIMD_MAX_BYTES`.
5. **Set the two variables** to the contents of `oidf-cimd-clients.json` and `oidf-cimd-trust-bundles.json`, and set
   `OIDF_ATTESTATION_ISSUER_ENABLED=true` in production.
6. **Register each client in PingFederate under its new id**, with the same settings and JWKS as the old client.
   Whether PingFederate authenticates a client whose id is an https URL with a path through the attestation filter is
   still to be shown on a licensed rig (U-0610); try it on a staging node first.
7. **Rename its `OIDF_BRIDGE_SIGNING_KEYS` entry** to the new id, keeping its key and its `attesters` list. An
   entry that names no attesters is refused, so the renamed entry still needs them.
8. **Unset `OIDF_ATTESTER_CIMD_URL`** and `oidf.attester.cimd.url`, then run the preflight.
9. **Retire the old clients** once the new ones work.

### How to tell it worked

- `python3 tools/cimd-split.py --check --out-dir cimd/` exits 0.
- The preflight prints no line naming `OIDF_ATTESTER_CIMD_URL`, `OIDF_CIMD_CLIENTS` or `OIDF_CIMD_TRUST_BUNDLES`.
- `/.well-known/client-attestation-service` lists `cimd` in `client_metadata_sources_supported`.
- One issuance per converted client, at `/federation/attestation`, returns an attestation whose `sub` is the client's
  URL, and a token request with it at `/as/token.oauth2` succeeds.
- server.log has no `attestation.issuer.cimd.document_refused` or `attestation.issuer.cimd.client_dropped` event for
  the new clients.

## Required claims and the attestation error code

**Who this is for.** Anyone who sets `OIDF_ATTESTATION_REQUIRED_CLAIMS` (or `oidf.attestation.required.claims`), or a
client's `attestation_required_claims`, to a name other than `workload`, `authorization_details` or `agent_id`; and
anyone whose clients or monitoring read the token endpoint's error code.

Until 0.8.0 a required-claim name the verifier did not know was treated as satisfied, with one warning in the log,
so a misspelling such as `agentid` switched its requirement off (F-0735). From 0.8.0 any such name is a presence
check: the attestation must carry the claim with a value other than null, or the token request is refused with 401
`insufficient_disclosure`. A misspelled name now refuses every request that needs it.

Refusals of the attestation or its proof of possession now answer `invalid_client_attestation`, not
`invalid_client` (draft-ietf-oauth-attestation-based-client-auth-11 §7.4). `invalid_client` stays for a request with
no attestation or no proof, a `client_id` other than the attestation's `sub`, and a server that cannot check the
proof. Both are 401.

### Steps

1. **List the names in use.** Read `OIDF_ATTESTATION_REQUIRED_CLAIMS` and each client's
   `attestation_required_claims` extended property.
2. **Compare them with what your attesters mint.** Decode one attestation per attester and check that each name is a
   top-level claim with a value. Correct a misspelling before upgrading; remove a name you do not need.
3. **Update anything that reads `invalid_client`.** A client SDK, a dashboard or an alert that treats `invalid_client`
   as "the client is unknown" sees `invalid_client_attestation` for a bad attestation or proof after the upgrade.

### How to tell it worked

- At start, server.log has one `attestation required claim <name>: <check>` line per global name, each spelled as
  you meant it.
- Token requests from each attested client still succeed; none is refused with `insufficient_disclosure`.

## External ceilings

**Who this is for.** Anyone who sets `OIDF_ATTESTER_FEDERATION_ENTITY` or `OIDF_CIMD_CLIENTS` under the production
profile. From 0.8.0 the attester caps what those clients may be granted with `OIDF_ATTESTER_EXTERNAL_CEILINGS`, and
in production it refuses an external client with no cap. If you set neither source, or run the development profile,
nothing here stops a client; development only logs one WARN per uncapped client.

A federation entity and a CIMD document each declare their clients' ceilings, and before 0.8.0 the attester granted
whatever they declared (F-0621). The cap is the operator's policy over that: every declared ceiling is narrowed to its
meet with the cap, never widened (the attester README).

### Steps

1. **List what each external client should get at most.** For each federation client id and each CIMD client URL,
   write the widest `authorization_details` you are willing to grant it. A `"*"` entry covers every client you do not
   name.
2. **Set `OIDF_ATTESTER_EXTERNAL_CEILINGS`** to that object before you deploy 0.8.0, for example
   `{"*": [{"type": "sales_agent", "sales_regions": ["EMEA"]}]}`.
3. **Group a federation entity's instances by client if you split them.** An entity that listed one client's
   instances under different `client_id`s to get around the one-instance-per-client limit can now list them all under
   one: every entry naming a client is one instance of it. The entries for one client must agree on `issuer`,
   `evidence_type`, `trust_domain`, `evidence_issuer`, `bundle`, `bundle_url` and `ttl`. An entity can also set each
   client's client-level ceiling in a `spiffe_client_ceilings` claim beside the bindings.

### How to tell it worked

- server.log has no `attestation.issuer.client_refused` event with reason `no_external_ceiling`.
- `oidf_attester_external_ceiling_capped_total{source}` counts the clients whose declared ceilings the cap narrowed;
  each also logs `attestation.issuer.external.ceiling_capped`. A count you did not expect means a source declares more
  than you capped, which is the cap working.
- One issuance per external client returns an attestation whose `authorization_details` sit within its cap.

## SPIRE

**Who this is for.** Anyone who sets `OIDF_ATTESTER_SPIRE_ENTRIES_URL` (or `oidf.attester.spire.entries.url`), and
anyone whose relying parties, token mappings or policies read `workload.attributes.selectors` or
`workload.attributes.spire` from an attestation. From 0.8.0 the setting is a removed name, refused on the settings
catalogue's first read in every profile and naming `OIDF_ATTESTER_SPIRE_READER_URL`, so the attester is
`FAILED_CONFIG` (`/federation/attestation` answers 503) until it is unset. Attestations no longer carry either
attribute, in any profile: whoever answered the old URL chose what the attester signed (F-0140).

The attester now reads SPIRE through the SPIRE entry reader over mutual TLS. Its selectors become verified evidence
selectors (`spire:*`, only those every registration entry for the SPIFFE ID shares) for the attester's own policy,
and are never signed into the attestation. The
attester README describes the settings and failure modes.

### Steps

1. **Move policy off the old attributes.** Find every reader of `workload.attributes.selectors` or `.spire` in token
   mappings, relying parties and PDP policies; they get nothing from 0.8.0. Selector-conditioned ceilings belong in
   the attester (B09).
2. **If you used SPIRE selectors, deploy the reader** (`services/spire-entry-reader`)
   beside SPIRE Server.
3. **Create a PingFederate SSL client key pair** in the admin console and add its SPKI to the reader's allowed
   clients.
4. **Set the reader settings:** `OIDF_ATTESTER_SPIRE_READER_URL` (https), `OIDF_ATTESTER_SPIRE_READER_TRUST_DOMAIN`,
   `OIDF_ATTESTER_SPIRE_READER_CA_FILE` and `OIDF_ATTESTER_SPIRE_READER_CLIENT_KEY_PAIR` (the key pair's alias).
   `OIDF_ATTESTER_SPIRE_FAILURE_MODE` is `closed` by default. With the reader set, a `spiffe-jwt` workload outside its
   trust domain, or one SPIRE has no entry for, is refused 403 in either mode. Under `closed`, a reader that cannot
   be read refuses 503; under `downscope` the attester issues without `spire:` selectors.
5. **Unset `OIDF_ATTESTER_SPIRE_ENTRIES_URL`** and `oidf.attester.spire.entries.url`, then run the preflight.

### How to tell it worked

- The preflight prints no line naming `OIDF_ATTESTER_SPIRE_ENTRIES_URL` or an `OIDF_ATTESTER_SPIRE_READER_*` setting.
- The start-up log has `attestation issuance: SPIRE reader <url> for trust domain <domain>` when the reader is set.
- One issuance for a SPIFFE workload succeeds, and server.log has `attestation.spire.read` with outcome `success`.

## After the first boot

1. **The start-up audit** in server.log: each JDBC store's schema check `CURRENT` for its family, with the head the
   release carries - federation V107 and agent V202 (platform V10 and ssf V310 are unchanged) - and nothing `REFUSED`
   or `FAILED_CONFIG` you did not mean ([startup-audit.md](../startup-audit.md)).
2. **Ready**: `GET /agentic-identity/health/ready` answers 200 only when every enabled component is `READY` or
   `DEGRADED` ([health.md](../health.md)).
3. **Refresh-token binding**: `oidf_attestation_refresh_binding_total` counts binds as attested clients get tokens, and
   `outcome="unknown_allowed"` refreshes of tokens issued before the upgrade fall towards zero
   ([metrics.md](../metrics.md)).
4. **Revocation**: with a register configured, `oidf_client_revocation_checks_total` counts checks, and no
   `status="unavailable"` you did not expect.
5. **Each feature you turned on**: the "How to tell it worked" of the sections above, and the feature's own events in
   the event catalogue.

## Rollback to v0.7.0

The migrations are forward-only: there is no down script. The clean way back is the backup taken before "The database,
first", restored with the v0.7.0 artefacts or image and PingFederate's configuration archive from before the upgrade;
anything written after the upgrade is lost with it. Pointing a v0.7.0 node at the migrated database was not tried for
this release. From the migrations themselves: V107, V201 and V202 only add columns, a table, indexes and constraints,
and every new column is nullable or has a default, so v0.7.0's writes still satisfy them; but v0.7.0 reads none of
them, so a suspended or revoked agent is attested again, and a self-signed hosted entity is not served from its stored
keys. Remove v0.8.0's new settings before a production rollback, or run the v0.7.0 preflight against the file first:
v0.7.0 refuses unknown `OIDF_` names of a family under production.
