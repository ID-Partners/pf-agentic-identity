# 0.7.0 (2026-10-11) - Phase 4: durable, clustered and rotatable

0.7.0 is Phase 4 of the production programme. Its exit criterion was a green cluster verification suite, key rotation
without a restart, a leased SSF engine and licensed CI running, and each is met: PingFederate can run as a console and engines (two in the suite) with JDBC client storage, `jdbc` leases and SSF on the `tables` dialect, and the suite that proves
it runs weekly on the self-hosted runner. The database schema belongs to a new migration runner, `oidf-db-migrate.jar`
(a release asset), and each store checks at start-up that its database is not behind the release. The SSF transmitter
is an engine: push streams leased one deliverer at a time with a fencing epoch, a worker pool that reads RFC 8935's
answers, dead SETs kept, paused streams that hold their events, an emission outbox any node fans out, and a shared,
durable receiver inbox. The federation's signing key follows PingFederate's without a restart, behind an activation
delay; foreign subordinates are pinned, with held rollovers and approvals. There is a Prometheus endpoint over every
loaded copy's metrics, one logger with PingFederate's correlation ids on every line, SpotBugs with find-sec-bugs in
every build, and boot-smoke, the six conformance plans and the cluster suite as licensed jobs that a release needs green.
Every finding targeted at 0.7.0 is closed, accepted in writing by David, or retargeted with a dated reason.

**The clustering claim is narrow.** The suite drove PingFederate's clients and tokens, the `jdbc` leases and SSF's
transmitter across two engines. Federation, client attestation, automatic registration, the SSF receiver, hosting, the
operator APIs and FAPI are not verified on a cluster in 0.7.0 ([F-0601](../findings.md#f-0601), high, 0.8.0;
[U-0601](../findings.md#u-0601)): run them on one node, or test them on your cluster yourself.
[deployment-limits.md](../operator/deployment-limits.md) says what is supported.

**Read "Before you deploy" first.** The items are in package order; [the upgrade
guide](../operator/upgrading/0.6.x-to-0.7.0.md) puts them in the order to do them. Above all, **the database comes
first**: 0.7.0 creates and alters no table, and a store whose database is behind the release is `FAILED_CONFIG` at
start-up, which is not retried. Before the first 0.7.0 boot, hand the 0.6.x tables to a migrator role, run
`oidf-db-migrate.jar adopt` for each family the database already has (federation at V103, agent at V200, SSF at V301),
then `migrate` and `grants --apply`. The items that stop a deployment are:

- the migrations - **Run `oidf-db-migrate.jar` before you start 0.7.0 PingFederate.** (MIG), with **Rerun `grants`
  before the new PingFederate starts.** and **Migrate first, then start PingFederate; restart it after a late
  migrate.** (SCHEMA); SSF's V303 to V310 (**Apply SSF migrations V303-V305, then the grants again.**, S10A, and the
  items of S10B, S10C, S10D, S10E and T6 that name V306 to V310), the federation family's V104 to V106 (S6B, S7A,
  S7B), and the platform family's V10 for a clustered node (**Clustered nodes need V10 and
  `OIDF_LEASE_BACKEND=jdbc`.**, LEASE);
- an `ldm` SSF store - **Grant `SELECT` on `idm.schema_migration` for an `ldm` SSF store.** and **An Identity Object
  Model database not built through the model repository's migrations has an empty ledger.** (SCHEMA);
- the topology - **Say what each node is, if PingFederate does not.** and **Do not run a clustered node on
  `in-memory-state`.** (TOPO), **SSF on a cluster needs the `tables` dialect.** (S10A) and **Turn key history on for
  a clustered node.** (S6B);
- removed or stricter settings - **Unset the signingAlgorithm init-params.** (S6A), **Unset
  `OIDF_SSF_PUSH_RETRY_MAX_ATTEMPTS`; `OIDF_SSF_PUSH_PAUSE_AFTER_SECONDS` replaces it.** (S10C), **Check the new bounds
  before you upgrade.** and **List any other transmitter origin your receiver uses.** (S10B), **Raise a grace shorter
  than your longest Trust Mark or registration.** (S6B), **Pin every subordinate before a production node starts.**
  (S7A), **Give the SSF receiver https URLs in production.** and **Make Kafka buildable, or switch it off.** (T2),
  **List the browser origins that read the federation, SSF or CAS metadata documents.** (T4), the strict readers of
  T1 and **Keep direct JDBC URLs off production.** (JDBC);
- operator and token clients - **Update operator clients to answer `use_dpop_nonce`.**, **Set
  `OIDF_OPERATOR_API_ENABLED=true` in production if the operator API is configured.** and **Stop sending gm-api
  string-form or malformed `act` claims.** (T5B), and **Stop sending authorization_details on ID-JAG token
  exchanges.** (T5A).

The rest ask for a check or a small change: SSF answers and retries read as RFC 8935 reads them, paused streams that
hold their events and a disable that deletes the queue, long polls held in PingFederate, a logout signal raised on
the user's confirmation, the federation's signing lagging PingFederate's key change by the activation delay, held
subordinate rollovers and approved pin changes, new log suffixes and refusal references, the metrics scrape, and the
driver's timeouts on each JDBC URL.

## Before you deploy

1. **Follow the upgrade guide, which puts these items in the order to do them.**
   [docs/operator/upgrading/0.6.x-to-0.7.0.md](../operator/upgrading/0.6.x-to-0.7.0.md) starts with the preflight run
   and the migrations - `adopt` for each family a 0.6.x database already has, then `migrate` and `grants` - and lists
   every item below by its bold title in upgrade order, grouped by area; it also covers clustering, key rotation
   without a restart, a rollback to 0.6.x (the migrations are forward-only) and what each consumer of this repository
   changes. The numbered items below are in package order, the order the packages' notes were folded in, not the
   order to do them in.
2. **Run federation, attestation, automatic registration and the SSF receiver on one node, or test them on your
   cluster yourself.** (C7) The reference cluster switches them off, so the suite never drove a challenge on one engine
   and a token on the other, a replayed proof or an engine-written registration (F-0601, U-0601, 0.8.0).
3. **Plan on a disabled client working for a minute on the other engines.** (C7) With PingFederate's JDBC client storage
   an engine serves a client it has cached for about a minute after the client is disabled, its secret changed or
   it is deleted (60.4 s at most over 20 trials on 13.1.3.0); a new client is seen at once. Revoke a compromised
   client's tokens as well as disabling it, and allow the minute in a runbook that relies on a disable.
4. **Have your load balancer follow engines by name.** (C7) An engine replaced in a rolling upgrade can come back on a new
   address; a load balancer that resolved it once keeps sending to the old one. In HAProxy, a `resolvers` section and
   `resolvers <name> init-addr last,libc,none` on the servers, as `reference/cluster/haproxy/haproxy.cfg` has.
5. **Restart a new engine once after its first replication if its outbound calls trust a private CA.** (C7) Until
   F-0585 is fixed, an engine's modules trust only the CAs PingFederate held when the JVM started; a new engine gets
   the configuration's trusted CAs with its first replication.
6. **Run the licensed jobs on the commit you tag.** (CI7A) Release now needs a green licensed run on the tagged commit. The
   licence file is on the runner (the `runner` user's `~/.pingidentity/config`, mode 600, owned by
   `runner`; docs/development/ci-runners.md, "Licensed jobs", has the command that writes it, which asks for the
   values instead of taking them on the command line). Run `gh workflow run licensed.yml --ref main -f suites=all -f required=true`
   on the commit to be tagged and wait for it to go green: the runner takes one job at a time, and boot-smoke, the six plans and the cluster
   job came to about an hour and a half of jobs on 2026-10-08.
7. **Set the driver's timeouts and `sslmode=verify-full` on each data store's JDBC URL.** (JDBC) The modules now bound a
   statement once it runs; opening a connection, a socket that stops answering and a statement nobody is left to
   cancel are the driver's and the server's to bound. Add `connectTimeout`, `socketTimeout`, `loginTimeout`,
   `tcpKeepAlive=true` and `sslmode=verify-full` with `sslrootcert` to the PingFederate data store's URL, and give
   the role it connects as a `statement_timeout` (`ALTER ROLE ... SET statement_timeout = '30s'`), as
   [docs/operator/database.md](../operator/database.md) describes.
8. **Expect a statement that runs longer than 10 seconds to fail.** (JDBC) Each store operation now has a 10-second
   deadline, and the driver cancels a statement still running when it passes (with PgJDBC a `PSQLException`,
   SQLState `57014`, `query_canceled`), where before it waited without limit. A statement the store would make
   after the deadline has passed is not made at all (`SQLTimeoutException`, SQLState `HYT00`). A store operation that ran that long before was a database in trouble; look at the
   database, not at the timeout.
9. **Keep direct JDBC URLs off production.** (JDBC) `OIDF_AUTHORITY_JDBC_URL`, `OIDF_SSF_JDBC_URL` and the instance
   registry's "JDBC URL" field were already `forbidden-in-production` in their catalogues, so the start-up audit
   refused them; from 0.7.0 the authority's stores and the SSF store also refuse a direct store in code under the
   production profile, a PostgreSQL URL included. Use the data store setting instead.
10. **A Redis password with `+` or a double-escaped `%` changes meaning.** (LEASE) From 0.7.0 the userinfo of `OIDF_REDIS_URL`
    (or `REDIS_URL`) is percent-decoded once, where 0.4.0 to 0.6.x decoded it twice and turned
    `+` into a space. A password written as `a+b` was sent as `a b` and is now sent as `a+b`; one written `%2525` was
    sent as `%` and is now `%25`. Write the password with each reserved character percent-encoded once (`+` as `%2B`
    if you mean a plus, a space as `%20`), and check that every node still authenticates to Redis after the upgrade.
11. **Clustered nodes need V10 and `OIDF_LEASE_BACKEND=jdbc`.** (LEASE) On a clustered production node (`OIDF_CLUSTER_MODE`
    or `pf.operational.mode` one of the `CLUSTERED_*` modes), apply the platform family's V10 (`oidf-db-migrate.jar
    migrate`, then `grants` for the runtime role) to the PostgreSQL database of a PingFederate data store, and set
    `OIDF_LEASE_BACKEND=jdbc` and `OIDF_LEASE_DATA_STORE_ID` on every node. Without them the node keeps refusing
    SSF_RECEIVER and AUTO_REGISTRATION, with a reason that names `OIDF_LEASE_BACKEND`.
    A lease database behind V10 (or drifted under production) refuses the backend at start-up the same way, with
    SCHEMA's reason naming `migrate`.
    SSF on a clustered node needs the `tables` dialect rather than a lease backend (**SSF on a cluster needs the
    `tables` dialect.**). A standalone node needs nothing: unset is `local`.
12. **The registration sweeper's first pass now runs at start-up.** (LEASE) It used to wait one interval; under its lease it
    runs as soon as the node takes the lease, then every `OIDF_REGISTRATION_SWEEP_INTERVAL_SECONDS`. A deployment
    with expired federation registrations sees them disabled within seconds of the upgrade rather than after the
    first interval.
13. **Run `oidf-db-migrate.jar` before you start 0.7.0 PingFederate.** (MIG) 0.7.0 creates and alters no table: a
    store whose database is behind the release is `FAILED_CONFIG` at start-up, naming the family and the command
    (**Migrate first, then start PingFederate; restart it after a late migrate.**). On a database 0.6.x built,
    first hand its tables to the migrator role, as a superuser (`ALTER TABLE ssf_streams OWNER TO oidf_migrator;` and
    the same for each table the database has - the operator page lists them). The 0.6.x tables belong to the role
    that created them, usually PingFederate's, and without this `migrate` stops at V302 with `must be owner of table
    ssf_streams` (rolled back, exit 1). Then adopt each family it has at the version 0.6.x left it at, and migrate,
    as the migrator role:

    ```sh
    java -jar oidf-db-migrate.jar adopt --family federation --baseline 103   # if the authority's tables are there
    java -jar oidf-db-migrate.jar adopt --family agent --baseline 200        # if agent_identity is there
    java -jar oidf-db-migrate.jar adopt --family ssf --baseline 301          # if the SSF store ran with storeDialect=tables
    java -jar oidf-db-migrate.jar migrate
    java -jar oidf-db-migrate.jar grants --runtime-role <PingFederate's role> --apply
    ```

    with `--jdbc-url` (or `OIDF_DB_MIGRATE_JDBC_URL`, `sslmode=verify-full`), `--user` and `--password-file`. A new
    database needs only `migrate` and `grants`. [Database migrations](../operator/database-migrations.md) has the
    roles, the refusals and what to do when adopt reports a difference.
14. **Scrape each node, not the load balancer.** (O5) The counters are the node's. Point Prometheus at every node's runtime
    port with `metrics_path: /agentic-identity/metrics`.
15. **In production, give Prometheus a key, not a secret.** (O5) Prometheus has no DPoP and PingFederate 13.x issues no
    certificate-bound token, so production takes Prometheus's unbound token only from a client `OIDF_METRICS_CLIENT_IDS`
    names. In PingFederate: an RSA key and certificate for Prometheus; an IdP connection of type **OAuth Assertion
    Grant** whose partner entity ID is the assertion's `iss` and whose verification certificate is that certificate,
    mapping into the operator access token manager; a client (`prometheus`) with the **extension grants** grant type,
    the scope `oidf.metrics.read`, no secret, and a short token lifetime; leave "Allow unidentified clients to request
    extension grants" clear. On this server, `OIDF_METRICS_CLIENT_IDS=prometheus`. In `prometheus.yml`:

    ```yaml
    oauth2:
      client_id: prometheus
      grant_type: urn:ietf:params:oauth:grant-type:jwt-bearer
      client_certificate_key_file: /etc/prometheus/oidf-scraper.key
      client_certificate_key_id: oidf-scraper-1
      token_url: https://pf.example.com/as/token.oauth2
      scopes: [oidf.metrics.read]
      endpoint_params:
        client_id: prometheus
    tls_config:
      ca_file: /etc/prometheus/pf-ca.pem
    ```

    A scraper that can send a `private_key_jwt` client assertion uses a Private Key JWT client with the
    client-credentials grant instead. Development and staging scrape with any bearer token. The full steps are in
    [docs/operator/metrics.md](../operator/metrics.md#authentication).
16. **Sum over `copy`, or keep it.** (O5) A family such as `oidf_events_total` is counted by each copy; a dashboard that
    wants the node's total sums over `copy`. Take `max` of the SSF backlog gauges across nodes, not `sum`: every node
    counts the same cluster tables.
17. **Expect the RAR plugin's and gm-api's lines at their own level.** (O6) They leave `ERROR [SystemErr]`: an alert or a
    filter that matched `ERROR [SystemErr]` with `com.pingidentity.ps.oidf.rar` or `au.com.idpartners.gm` in it matches
    nothing now; match the logger names instead, at `WARN` and `ERROR`.
18. **Turn the RAR plugin's summary line back on if you read it.** (O6) `RAR governance: type=...` is `DEBUG`: add
    `<Logger name="com.pingidentity.ps.oidf.rar.AttestationAwareRarProcessor" level="DEBUG"/>` to `log4j2.xml`
    (PingFederate re-reads it within 30 seconds).
19. **Look up a refusal's reference as PingFederate's id.** (O6) A reference quoted in an `error_description`, a federation
    refusal (`ref=`) or the attester's `X-Correlation-Id` is now PingFederate's tracking id or request id rather than
    `oidf-` and eight hex digits: search `server.log` for it as it is. The image's `log4j2.xml` prints the request id
    in `server.log`'s third column; a server profile that brings its own `log4j2.xml` replaces that file, so add
    `%X{httprequestid}` to its `server.log` pattern, and a parser that splits that file's columns must expect the new
    one. To have a caller's own correlation id there, set PingFederate's `requestHeaderForCorrelationId`
    (admin API `/serverSettings/generalSettings`) to the header it sends.
20. **Check a log parser against the new suffix.** (O6) Every line of this repository's ends with `ctx[...]`; a parser that
    reads the message to the end of the line sees it. Set `OIDF_LOG_CORRELATION=off` if you print the ids in the
    pattern instead.
21. **Apply SSF migrations V303-V305, then the grants again.** (S10A) On an SSF `tables` database run `oidf-db-migrate.jar
    migrate` before PingFederate starts 0.7.0, then `grants --runtime-role <role>` again and apply what it prints: V304
    adds the sequence `ssf_pending_sets_seq`, and the runtime role needs `USAGE` on it to queue a SET. Without V303-V305
    SSF does not start (its schema check names the family and `migrate`); without the grant every SET the transmitter
    queues fails with `permission denied for sequence ssf_pending_sets_seq`. The backlog already queued keeps its order.
22. **SSF on a cluster needs the `tables` dialect.** (S10A) A clustered production node now starts SSF on
    `OIDF_SSF_STORE_DIALECT=tables` (the default) with V303-V305 applied, and no lease backend setting is needed for it.
    On `ldm` it is refused, with a reason naming `OIDF_SSF_STORE_DIALECT=tables`: `ldm` is single-node in 0.7.0. A
    standalone node runs either dialect as before.
23. **A receiver may see a SET twice after a node fails.** (S10A) When a node dies, or stalls past its lease, mid-POST, the
    next node to take the stream posts its first SET again, no sooner than `OIDF_SSF_STREAM_LEASE_SECONDS` later and
    possibly well after, while the surviving nodes finish the streams they are serving. RFC 8935 §2 allows the resend;
    a receiver deduplicates by `jti`.
24. **Apply SSF migration V306 before PingFederate starts 0.7.0, then the grants again.** (S10B) On an SSF `tables` database
    run `oidf-db-migrate.jar migrate` (V306 creates `ssf_dead_sets`) and `grants --runtime-role <role>` again, and
    apply what it prints. Without V306 SSF does not start: its schema check names the family and `migrate`. Without
    the grant a receiver's `invalid_request` and every poll `setErrs` fail with `permission denied for table
    ssf_dead_sets`.
25. **Expect 200 and 204 to count as delivered, and a 400 without `invalid_request` to be retried.** (S10B) Up to 0.6.x a
    204 was retried towards the dead-letter pause, and every 400 dropped its SET whatever its `err`. A receiver that
    answers 400 `invalid_audience` or `invalid_issuer`, 404 or 410 now pauses its stream with the reason in
    `status_reason`, all its SETs kept: fix the receiver or the stream, then resume it through the stream API. Watch
    `ssf.push.stream_paused` and `ssf.push.delivered_nonstandard`.
26. **A push endpoint the outbound policy refuses pauses its stream.** (S10B) Up to 0.6.x each SET to it was dropped. Fix
    the endpoint (or `OIDF_FETCH_HOST_ALLOWLIST` for a legitimate internal receiver) and resume the stream.
27. **Check the new bounds before you upgrade.** (S10B) `OIDF_SSF_PUSH_RETRY_BACKOFF_SECONDS` must be 1-60 and
    `OIDF_SSF_POLL_MAX_EVENTS` 0-1000; a value outside them was read before and now leaves SSF `FAILED_CONFIG`, naming
    the setting. A cluster has at most `OIDF_SSF_PUSH_WORKERS` times its nodes POSTs in flight (8 on two nodes at the
    default): size it against your receivers.
28. **List any other transmitter origin your receiver uses.** (S10B) If the transmitter you poll or manage a stream at names a
    `configuration_endpoint` or a poll `endpoint_url` at an origin other than
    `OIDF_SSF_RECEIVER_TRANSMITTER_CONFIGURATION_URL`'s, `SSF_RECEIVER` is now `FAILED_CONFIG` and no token is sent
    there: add the origin to `OIDF_SSF_RECEIVER_TRANSMITTER_ORIGINS` (`https://host[:port]`, comma-separated).
29. **Apply SSF migration V308 before the new jar starts.** (S10C) On the `tables` store every stream read now selects
    `ssf_streams.row_version`, `last_activity_at` and `paused_by`, and the push engine writes
    `ssf_stream_lease.failing_since`; without them SSF fails at its first read. Run
    `java -jar oidf-db-migrate.jar migrate --family ssf` against the SSF database
    ([database-migrations.md](../operator/database-migrations.md)). V308 adds columns only, so the runtime role's
    grants are unchanged. The `ldm` dialect has no `ssf` family and keeps these per node (F-0555).
30. **Unset `OIDF_SSF_PUSH_RETRY_MAX_ATTEMPTS`; `OIDF_SSF_PUSH_PAUSE_AFTER_SECONDS` replaces it.** (S10C) A deployment that
    still sets the old name (or `oidf.ssf.pushRetryMaxAttempts`, or the `pushRetryMaxAttempts` init-param) is refused:
    SSF is FAILED_CONFIG with an ERROR naming it. A push stream whose receiver is down is now retried, on the backoff, for 24 h by default
    (300 to 604800 s) before it is paused, where it used to pause after about 75 s. Keep `OIDF_SSF_SET_TTL_SECONDS`
    (7 days by default) longer than the window: a shorter TTL expires a failing stream's SETs before it is paused, and
    start-up WARNs about it.
31. **Expect paused streams' queues to grow, and alert on the trim.** (S10C) A stream paused by its receiver or by this
    transmitter now holds up to `OIDF_SSF_STREAM_QUEUE_MAX` SETs (10,000; 100 to 100000) until they expire. Size the
    SSF database for it, and alert on `oidf_ssf_queue_trimmed_total` or the WARN: a trim drops the oldest held SETs.
32. **Know that a disable deletes the queue.** (S10C) A receiver that sets its stream to `disabled` loses what was queued for
    it (SSF 1.0 §8.1.2.1), where up to 0.6.x those SETs were kept until their TTL. Use `paused` to keep them.
33. **Check `inactivity_timeout` before upgrading.** (S10C) With `OIDF_SSF_INACTIVITY_TIMEOUT_SECONDS` set (0, none, by
    default), a stream whose receiver makes no management call and no poll for that long is now paused, with a
    stream-updated SET. V308 starts every stream's counter at the upgrade, so none is paused for idleness before it.
34. **Grant `ssf.admin` to the operators who may pause, resume and retry streams.** (S10C) The routes take a PingFederate
    access token with the scope, DPoP-bound in production, as every operator route does
    ([operator-authentication.md](../operator/operator-authentication.md)); they are rate-limited and audited.
35. **Apply SSF migration V309, then run `grants` again, before the new jar starts.** (S10D) On the `tables` store every
    raised event is written to `ssf_emission_outbox` (with a new id sequence) and every logout hint to
    `ssf_logout_replay`; `ssf_pending_sets` gains `emission_id`. Without the tables, or the runtime role's grants on
    them and on `ssf_emission_outbox_id_seq`, raised events stay in each node's hand-off and `POST /ssf/events:emit` and
    SCIM answer 500. Run `java -jar oidf-db-migrate.jar migrate --family ssf` and then
    `grants --runtime-role <role> --apply` against the SSF database
    ([database-migrations.md](../operator/database-migrations.md)). SETs queued before the upgrade stay queued and go
    first. The `ldm` dialect has no `ssf` family; its outbox is in each node's memory.
36. **Read the bridge's return as "queued", not as a SET count.** (S10D) `SsfEventBridge.onSessionRevoked` and its siblings, the
    methods an OGNL expression or a hook calls, now return 1 when the event was queued and 0 when it was not (a
    duplicate within 5 s, the transmitter not started, a refused payload or a full hand-off). Before, they returned the
    number of SETs queued, which they no longer know: an expression that tested for a value above 1 should test for 1.
37. **Expect a SET's streams to be chosen about a second later.** (S10D) The fan-out runs every second, so a SET is minted for
    the streams that hear the event when a worker takes it, not when the event was raised; its `iat` is still the second
    it was raised. A subject added to a stream in that second hears the event; one removed does not.
38. **Size the hand-off for a store outage.** (S10D) What a node has queued and not written when it stops is lost, and a full
    hand-off drops each new event (`ssf.set.dropped` `queue_full`). While the store is down the hand-off fills at the rate
    events are raised; `OIDF_SSF_EMISSION_QUEUE_CAPACITY` (10000) bounds it. Alert on `ssf.outbox.write_failed` and on
    `queue_full`.
39. **Apply SSF migration V307, then run `grants` again, before the new jar starts.** (S10E) On the `tables` store the
    receiver writes every inbound SET to `ssf_receiver_inbox` and `ssf_receiver_set_errs`. Without them, or without
    the runtime role's grants on them, every pushed SET is answered 503 and no polled SET is acknowledged. Run
    `java -jar oidf-db-migrate.jar migrate --family ssf` and then `grants --runtime-role <role> --apply` against the
    SSF database ([database-migrations.md](../operator/database-migrations.md)). The `ldm` dialect has no `ssf`
    family; its inbox is in each node's memory.
40. **Expect the first boot to start with an empty inbox.** (S10E) A SET received before the upgrade and delivered again
    after it is acted on again. The instance registry's changes are idempotent, but a second grant revocation revokes
    any grant the user was issued since the first, so a user who signed in again in between loses that grant. A poll
    receiver acknowledges what the transmitter still holds from the poll it next makes.
41. **Watch for dead SETs.** (S10E) A SET whose handlers fail ten times (`OIDF_SSF_RECEIVER_ACTION_ATTEMPTS`) is no longer
    acted on: alert on `oidf_ssf_receiver_action_dead_total` or the ERROR line, and find the rows with
    `SELECT iss, jti, attempts, last_error FROM ssf_receiver_inbox WHERE state = 'dead'`
    (servlets/ssf/README.md).
42. **Unset the signingAlgorithm init-params.** (S6A) The federation servlet's and `/federation/register`'s
    `signingAlgorithm` init-params were removed; either one set stops its servlet starting, naming it. Set
    `OIDF_FEDERATION_SIGNING_ALG` instead. Neither servlet's shipped web.xml sets them.
43. **Expect registration responses signed with OIDF_FEDERATION_SIGNING_ALG.** (S6A) A deployment that set
    `OIDF_FEDERATION_SIGNING_ALG=PS256` now has its registration responses signed PS256 too; a relying party that
    accepted only RS256 there must accept the federation's algorithm. With the default nothing changes.
44. **Have a key for the algorithm before you choose ES256 or ES384.** (S6A) PingFederate must have an active P-256 (ES256)
    or P-384 (ES384) OAuth/OIDC signing key - its rotating keys include both - or the federation servlet does not
    start and SSF answers 503.
45. **Turn key history on in production.** (S6A) With `OIDF_FEDERATION_HISTORICAL_KEYS` off, a key rotated while a node runs
    stays in that node's `jwks` for its grace but is forgotten at a restart and cannot be revoked.
46. **Apply V104 before you start the new release.** (S6B) Run `migrate --family federation` (tools/db-migrate) against the
    authority's database - any deployment with `OIDF_AUTHORITY_DATA_STORE_ID` or `OIDF_AUTHORITY_JDBC_URL` set: the
    start-up schema check refuses a federation family behind the release, and the key observer needs
    `federation_key_observed`.
47. **Expect signing to lag PingFederate's key change by the delay.** (S6B) After you make a new key active in PingFederate,
    its tokens carry the new key at once, the federation's statements, Trust Marks and registration responses an hour
    later (the default). Set `OIDF_FEDERATION_KEY_ACTIVATION_DELAY_SECONDS=0` to sign with a new key from the observer's next tick, at the cost of
    peers with a cached Entity Configuration failing until they fetch it again.
48. **Raise a grace shorter than your longest Trust Mark or registration.** (S6B) Under the production profile the
    federation servlet (and the SSF transmitter and automatic registration, which share its keys) is FAILED_CONFIG when `OIDF_FEDERATION_KEY_HISTORY_GRACE_SECONDS` is shorter than any Trust Mark
    type's `lifetime_seconds`, `OIDF_REGISTRATION_MAX_TTL_SECONDS` or 3600; the message names the values. The defaults
    (86400 each) pass.
49. **Turn key history on for a clustered node.** (S6B) With `OIDF_FEDERATION_HISTORICAL_KEYS` off the key observations are
    kept in each node's memory; a clustered node under the production profile is REFUSED.
50. **Keep the leases in the authority's database to fence the observer.** (S6B) With `OIDF_LEASE_BACKEND=jdbc` and
    `OIDF_LEASE_DATA_STORE_ID` (or `OIDF_LEASE_JDBC_URL`) naming the same database as `OIDF_AUTHORITY_DATA_STORE_ID` (or
    `OIDF_AUTHORITY_JDBC_URL`), the observer's writes check the lease in their own transaction; otherwise a start-up
    WARN says they are fenced only by the lease's local clock (F-0525); a standalone node on the `local` lease backend has
    no second writer and gets no WARN.
51. **Pin every subordinate before a production node starts.** (S7A) Under `OIDF_DEPLOYMENT_PROFILE=production` an
    `OIDF_FEDERATION_SUBORDINATES` entry with no pin makes the federation servlet `FAILED_CONFIG`, naming the entries.
    For each, confirm its keys with its operator out of band (by RFC 7638 thumbprint), compare them with what
    `GET /federation/admin/subordinates?entity_id=` shows a development node saw, and enrol it

    [Operations](../federation/operations.md#pinned-subordinates) has the steps. Under development an unpinned

53. **Re-pin before a subordinate rolls its keys over.** (S7A) Its chains fail from the moment it signs with a key that is

54. **Migrate the authority's database to V106 first.** (S7B) Run `java -jar oidf-db-migrate.jar migrate --family
    federation` with this release's jar before PingFederate starts; the start-up schema check holds the family to what

67. **Give the SSF receiver https URLs in production.** (T2) An http `OIDF_SSF_RECEIVER_POLL_URL` or

69. **Expect the receiver to wait for its JWKS.** (T2) `SSF_RECEIVER` is not ready until the transmitter's JWKS has been

70. **Run the preflight again, naming the process.** (T2) `java -jar oidf-preflight.jar --process pingfederate --env-file
    FILE` (and `--format docker` for a Docker env file) now exits 1 on settings the server refuses when it reads them -

71. **Read the narrower refusals.** (T2) A governed federation-runtime, outbound-fetch, Redis, lease, authority-store or SSF
    setting now refuses the components that read it, not every component of its catalogue
    (settings-catalogue.md lists them). A dashboard or alert that
    expected, say, `ATTESTATION_AUTH` `REFUSED` for `OIDF_PDP_FAIL_OPEN=true` sees it `READY`; `OIDF_FETCH_ALLOW_HTTP`
    and `OIDF_AUTHORITY_JDBC_URL` now name more components than before (`SSF`, `SSF_RECEIVER` and `OPERATOR_API`, and
    `FEDERATION`), because those components read them.
72. **Expect the resolve cap to count more.** (T3) With the resolve endpoint enabled, one caller is given 30 resolutions a
    minute (`OIDF_FEDERATION_RESOLUTION_RESOLVE_SUBJECTS_PER_MINUTE`) that a kept response could not answer. Before,
    only distinct subjects counted, so a caller that repeated a failing resolution, or varied its trust anchors or
    entity types, was never refused; it now uses its allowance and is answered 503 `temporarily_unavailable` with a
    `Retry-After` past it. Raise the setting if a legitimate caller resolves more than that.
73. **List your load balancer in `OIDF_TRUSTED_PROXIES` if the resolve endpoint is behind one.** (T3) The resolve cap now
    counts the client address behind a listed proxy; unlisted, every client behind it shares one minute, as before. The
    `FEDERATION` part now reads the setting when the resolve endpoint is enabled: a value it cannot read stops it at
    start-up (`FAILED_CONFIG`, naming the setting), as it already stopped the challenge endpoints.
74. **Send signed request objects, or use PAR, for relying parties that renew automatically.** (T3) Under production an
    encrypted request object never registers or renews a relying party. From this release a renewal that falls due
    while the registration is current is deferred rather than refused, and the request goes on; watch for
    `federation.registration.refresh_deferred` with `encrypted_request_object`. If the relying party sends nothing
    signed before the registration expires, its next request is refused 400 `invalid_request_object`, as before.
75. **Apply FAPI 2.0 at device authorization.** (T3) For a client in `OIDF_FAPI2_CLIENTS` (or every client, with `*`), a
    client assertion at `/as/device_authz.oauth2` whose `aud` is the token endpoint URL is now refused 401
    `invalid_client`; address it to the issuer. Re-assemble `pf-runtime.war` from this release's image to pick up the
    mapping.
76. **List the browser origins that read the federation, SSF or CAS metadata documents.** (T4) Until 0.7.0
    `/.well-known/client-attestation-service`, `/.well-known/ssf-configuration` and every federation endpoint answered
    `Access-Control-Allow-Origin: *` (the federation's `corsAllowOrigin` defaulted to `*`). Now none answers CORS
    unless an origin is listed: `OIDF_ATTESTER_CORS_ORIGINS` for the CAS metadata (the attester's own setting),
    `OIDF_SSF_CORS_ORIGINS` for SSF, and the federation servlet's `corsAllowOrigin` init-param, now a list of
    `http(s)://host[:port]` origins. `*` in any of them stops that servlet at deploy (FAILED_CONFIG, 503), so remove a
    `corsAllowOrigin=*` you set. Servers, SDKs, the conformance suite and native clients are not affected; only a web
    page reading these documents from a visitor's browser is. A sweep of this repository on 2026-10-08 found no such
    page.
77. **Update any client that matches the issuance endpoint's error codes.** (T4) `POST /federation/attestation` now answers
    `invalid_instance_attestation` with 400 where it answered `invalid_svid` (401), `instance_not_authorized` (403)
    where it answered `spiffe_id_not_authorized`, `invalid_client` with 401 rather than 400, and
    `invalid_instance_attestation` and `invalid_instance_proof` with 400 rather than 401. The 429 of the per-address
    limit is unchanged. Logs and the refusal metrics keep the old internal reasons. A sweep of this repository found
    no client matching the old codes; the harness's line now names the new one.
78. **Expect IPv6 callers to share an allowance per /64.** (T4) The challenge endpoints, the issuance endpoint and the
    operator APIs' failed-authentication limit now count an IPv6 client by its first 64 bits; IPv4 and IPv4-mapped
    addresses are counted as before. Set `OIDF_RATE_LIMIT_IPV6_PREFIX=128` to count each address alone again, or a
    shorter prefix (down to 32) for networks that hand out larger blocks. A value outside 32-128 stops the challenge
    endpoints and the attester's servlets at deploy, and gm-api's grant-management metadata servlet too, since it
    checks the trusted-proxy settings at start although it keys no rate limit.
79. **Expect the engine's copy to start no background job but its Redis watchdog.** (T4) From 0.7.0 a managed executor
    starts only in the copy the webapp's lifecycle listener marked; the engine's copy logs "not the webapp's copy" at
    WARN for any other start. No job runs there today, so nothing should stop; a WARN of that kind in server.log names
    code that would have run a thread with nothing to stop it. The engine's copy still starts its own
    `redis-watchdog-<hash>` on its first Redis write.
80. **Check Kubernetes service-account names if a cluster uses unusual ones.** (T4) A GKE, EKS or AKS token whose
    namespace is not a DNS-1123 label (63 characters at most) or whose service account is not a DNS-1123 subdomain
    (253) is now refused `invalid_instance_attestation`, counted under `subject`. Kubernetes itself accepts no other
    names, so only a misbehaving cluster's tokens change.
81. **Set `OIDF_TRUSTED_PROXIES` where gm-api sits behind a proxy and has no `grantManagementEndpoint`.** (T4) Its metadata
    now ignores `X-Forwarded-Proto` and `X-Forwarded-Host` from anyone not listed, and advertises the URL the request
    itself reached. A configured `grantManagementEndpoint` is still used as given.
82. **Stop sending authorization_details on ID-JAG token exchanges.** (T5A) A client that asks for an ID-JAG with
    `authorization_details` is now refused. Until 0.7.0 PingFederate copied them into the ID-JAG unchecked; if a
    relying authorization server needs details in the ID-JAGs this server issues, write them in the SP connection's
    ID-JAG claim mapping from a source you trust, which PingFederate keeps in place of the request's. To find such
    clients, look for `idjag.details.refused` in server.log or the audit log after the upgrade. A token exchange for an
    ID-JAG without `authorization_details` is unaffected, and so is every other grant.
83. **Update operator clients to answer `use_dpop_nonce`.** (T5B) A client that sends a DPoP-bound token to an operator API
    (hosted-entity enrolment, the registered clients, the health detail, `/agentic-identity/info`) gets a 401 with
    `WWW-Authenticate: DPoP error="use_dpop_nonce"` and a `DPoP-Nonce` header on its first request; it must sign a new
    proof carrying that nonce and send the request again, and use the `DPoP-Nonce` a later answer carries. A client
    that does not fails every DPoP request after the upgrade. In development `OIDF_OPERATOR_DPOP_NONCE=false` turns it
    off until the client is updated; production refuses that value (every operator route answers 503 naming it). Run
    Redis on a cluster, or a client can be handed a nonce one node issued and another refuses.
84. **Set `OIDF_OPERATOR_API_ENABLED=true` in production if the operator API is configured.** (T5B) A production deployment
    that sets any of `OIDF_OPERATOR_AUDIENCE`, `OIDF_OPERATOR_BASE_URL`, `OIDF_OPERATOR_AUTH_MODE`,
    `OIDF_OPERATOR_JWKS_URL` or `OIDF_OPERATOR_INTROSPECTION_ENDPOINT` with `OIDF_OPERATOR_API_ENABLED` unset now
    starts the operator API FAILED_CONFIG, asking for the switch, rather than inferring it; the component's verdict
    names the switch and the setting that made it present.
85. **Stop sending gm-api string-form or malformed `act` claims.** (T5B) gm-api now refuses, as 401 `invalid_token`, a token
    whose `act` is a JSON object serialised into a string, is not an object at some level, names no `sub` or `iss` at
    a level, or nests deeper than 10. RFC 8693 §4.1: "The "act" claim value is a JSON object". This platform's own
    token-exchange mapping (`ClientAttestationUtils.delegationActChain`) emits the string form, and whether
    PingFederate can emit the object at all is still open (U-0009), so gm-api refuses every delegated token minted
    through that mapping, in every profile, until U-0009 is settled; gm-api has no development switch for it. Do not
    upgrade gm-api where it must accept delegated tokens from that mapping.
86. **Expect RAR decisions and refused attester clients in the audit log.** (T5B) Each `authorization_details` entry the
    RAR plugin decides is now one audit row (`protocol` `RAR`), and a misconfigured attester client one
    `attestation.issuer.client_refused` row. Size the audit log's destination for one row per decided entry, or set
    `OIDF_EVENTS_AUDIT=false` to keep events in `server.log` only - for every component in that JVM, not the plugin

87. **Apply SSF migration V310, then run `grants` again, before the new jar starts.** (T6) On the `tables` store the SCIM
    list reads the new key columns and index, and a logout writes `ssf_logout_pending`; without the table, or the runtime

    0.7.0 when it starts.
88. **Set proxy and receiver timeouts above the long-poll wait.** (T6) A poll that finds nothing is now held for up to
    `OIDF_SSF_POLL_LONG_POLL_WAIT_SECONDS` (10 by default) in PingFederate, where before it was answered at once. A load
    balancer, reverse proxy or receiver HTTP client that gives up sooner cuts the poll off; set each above the wait, or
    set the wait lower. A receiver that sends `returnImmediately: true` is unaffected.
89. **Look for duplicate userNames before the upgrade.** (T6) 0.6.x let two SCIM users share a userName that differs only in
    case or width. The store reports each such record at start-up (`ssf.scim.username_conflict`, and a WARN with the
    count) and leaves it without a key: it is not merged, it matches no `userName` filter, and the name is not unique
    until an operator renames one of each pair with `PUT` or `PATCH`. The unkeyed record can still be deactivated,
    updated or deleted under its old name; only a rename to a name another user holds is refused. To find them first, on the SSF database:
    `SELECT lower(user_name), array_agg(subject_key) FROM ssf_scim_users WHERE user_name IS NOT NULL GROUP BY 1 HAVING count(*) > 1;`
    (case only; width variants are found at start-up).
90. **Expect session-revoked after the confirmation, and none for a declined sign-off.** (T6) Up to 0.6.x the signal went out
    when `/idp/init_logout.openid` answered, before PingFederate asked the user; now it goes out when the user presses OK
    on PingFederate's "Logout Confirmation" and PingFederate answers the sign-off redirect to the
    `post_logout_redirect_uri` (or when it signs off without asking and answers that redirect), a few seconds later.
    Cancel, a closed tab, any other answer (an error or expired-state page) or 15 minutes without an answer raise nothing (`ssf.logout.signal.refused` `declined` or
    `not_confirmed`). The war must carry the new `SsfLogoutConfirm` filter: an image built from this release's
    `filters.xml` does; a hand-made `web.xml` must map `com.pingidentity.ps.oidf.servlet.ssf.LogoutConfirmFilter` over
    `*.ping`, or no logout raises a signal. A logout with no `post_logout_redirect_uri`, which PingFederate answers with
    a page rather than the redirect, raises no signal (F-0596, not measured on the rig).
91. **Say what each node is, if PingFederate does not.** (TOPO) A node whose `pf.operational.mode` is blank or unusual, or
    whose `OIDF_CLUSTER_MODE` disagrees with it, is now an unknown topology, and the production profile refuses every
    component on it. A standalone PingFederate whose `run.properties` says `STANDALONE` (the image's default) needs
    nothing. To check, read the start-up audit's `topology` line after the upgrade: `UNKNOWN` says why.
92. **Do not run a clustered node on `in-memory-state`.** (TOPO) A node that is `CLUSTERED_ENGINE`, `CLUSTERED_CONSOLE` or
    `CLUSTERED_DUAL` is refused every store kept in memory, whatever `OIDF_ACCEPTED_RISKS` accepts: set
    `OIDF_REDIS_URL` and the data store settings, or run one standalone node. On such a node FEDERATION and
    AUTO_REGISTRATION also need PingFederate's JDBC client storage, SSF_RECEIVER and AUTO_REGISTRATION
    need `OIDF_LEASE_BACKEND=jdbc` (**Clustered nodes need V10 and `OIDF_LEASE_BACKEND=jdbc`.**), and SSF the `tables`
    dialect (**SSF on a cluster needs the `tables` dialect.**). [docs/operator/clustering.md](../operator/clustering.md)
    lists every requirement.
93. **Expect 503 from the Trust Mark admin routes without a store.** (TOPO) In production without
    `OIDF_AUTHORITY_DATA_STORE_ID` (or `OIDF_AUTHORITY_JDBC_URL`), `/federation/admin/trust-marks` and its audit and
    revoke routes answer 503 unless the node is standalone with `in-memory-state` accepted; the rest of the admin API
    serves.

94. **Let image builds reach the Go module proxy.** (AGE) Only if you build the image yourself behind an egress
    allow-list: the build now pulls `golang:1.27.2-alpine3.24` from Docker Hub and fetches age's source from
    `proxy.golang.org`, checked against `sum.golang.org`, where it used to download age's release from `github.com`.
    A build that cannot reach them stops in the `age-build` stage. Nothing changes at run time: `age` is still

## What changes for readers of the repository

- **Two new modules and a new library.** `tools/db-migrate` builds `oidf-db-migrate.jar`, a release asset and a
  GitHub Packages artefact (MIG); `libs/migrations` holds the families, ordering and checksums the runner, the
  start-up check and testkit share; `services/cluster-suite` is the cluster verification suite (C7). The reactor
  lists 32 poms, and the BOM no longer manages H2 (F-0255).

  (`libs/openid-federation`), agent V200 (`libs/agent-registry`), ssf V300-V310 (`servlets/ssf`); a package that needs
  a number takes the next free one in its family (Phase 4 decision 4). Nothing creates or alters a table at start-up.

  profile, with the roles, migrations and client storage as jobs before PingFederate starts (REF); slot ports
  (`REF_SLOT`, `PF_RIG_SLOT`) give each stack or rig twenty ports from 57100.

  weekly against `conformance/expected/*.json` under `--strict-expectations`, the cluster suite weekly, all on the
  self-hosted runner `[self-hosted, pfai-linux]` from a licence file there; Release refuses a tag without them green
  (CI7A, C7). docs/development/ci-runners.md has the runner and "The risk, accepted".
- **Static analysis and log hygiene in CI.** SpotBugs 4.10.4 with find-sec-bugs 1.14.0 at `verify`, against
  `build/spotbugs/exclude.xml` (SBG); `tools/log-scan.py` refuses any logger but `PlatformLog` in shipped code (O6);

- **The findings digest.** `python3 tools/findings.py --digest` writes `docs/findings-digest.md`, published as
  `docs/findings.md` in the public tree; `--check` fails when it is stale (T3). The microsite publishes only what the

## Package S10C: Paused SSF streams hold their events, announce status changes, and pause after 24 h; an ssf.admin stream API

SSF 1.0 Final (fetched from openid.net 2026-10-07), §8.1.2.1, paused: "The Transmitter MUST NOT transmit events over
the stream. The Transmitter SHOULD hold any events it would have transmitted while paused, and SHOULD transmit them
when the stream's status becomes "enabled". The Transmitter MAY drop zero or more events that are held when the stream
is paused."; disabled: the transmitter "will not hold any events for later transmission". §8.1.2: "If a Transmitter
decides to enable, pause or disable updates from a stream independently of an update request from a Receiver, it MUST
send a Stream Updated Event". §8.1.5: "MUST send this event to the Receiver before stopping the stream" and "upon
re-enabling the stream"; its `sub_id` "MUST be of format opaque, and its id value MUST be the unique ID of the stream".

So a stream-updated SET goes with a transmitter's or an operator's change and not with the receiver's own, which its
200 answers. "Before stopping" and "MUST NOT transmit" are reconciled as notice-only delivery: a stream that is not
enabled is claimed while a stream-updated SET heads its queue, and is sent those and nothing else. Every status change
drops any stream-updated SET still queued, since it describes a status that no longer holds (the MAY drop). A notice
whose receiver still answers 404 or 410 is retried on the backoff rather than at once.

`sets:retry-dead` queues dead SETs again although RFC 8935 §2 says "In all other cases, the SET Transmitter SHOULD NOT
retransmit a SET": it is an operator's deliberate override for a receiver that has fixed what made it refuse them.

The SSF lease contract tests now run on a clock the test moves, and the tables store's lease rows are moved with it,
so they no longer fail under load (F-0557).

## Package S10D: An SSF emission outbox: one INSERT per event, fanned out once per stream by any node

Before this package the thread that saw an event did the whole fan-out: `SsfEventEmitter.emit` listed every stream and,
for each that subscribed, signed a SET, inserted it and published it to Kafka, one statement at a time. That thread
was PingFederate's - the audit appender's `append`, the logout filter after its chain, a hook - and Kafka's `send()`
could hold it for up to `max.block.ms`. A crash after the third stream's insert left the fourth without the SET, and a
store error made the bridge drop the event with a WARN.

Now `SsfEventBridge` builds the event (`SsfEventEmitter.sessionRevokedEvent` and its siblings) and offers it to the
node's `EmissionQueue`. One writer appends batches of up to 100 to the store's `EmissionOutbox`; the tables store's is
`JdbcEmissionOutbox`. `OIDF_SSF_OUTBOX_WORKERS` workers per node each take one row at a time:
`SELECT ... WHERE next_attempt_at <= now() AND NOT EXISTS (an older row about the same subject) ORDER BY id LIMIT 1
FOR UPDATE SKIP LOCKED`. Then the streams, a SET for each that subscribes (`iat` the second the event was raised),
`INSERT ... ON CONFLICT (emission_id, stream_id) WHERE emission_id IS NOT NULL DO NOTHING`, the row's `DELETE` and the
commit; Kafka after the commit. PostgreSQL 16's `SELECT` (fetched 2026-10-07): "With
SKIP LOCKED, any selected rows that cannot be immediately locked are skipped. ... can be used to avoid lock contention
with multiple consumers accessing a queue-like table." Its `INSERT`: "If an index_predicate is specified, it must, as a
further requirement for inference, satisfy arbiter indexes", and "Only rows that were successfully inserted or updated
will be returned", which is how the logout replay check returns nothing for a key still within its bound. Nothing in a
fan-out leaves the transaction - minting is local - so the row lock is the claim and a rollback the release, and no
lease is needed. A failed mint is rolled back to a savepoint taken after the lock, so the attempt is recorded before
another worker can take the row: 1 s, doubling to 60 s, dropped after `OIDF_SSF_OUTBOX_MAX_ATTEMPTS` (10). A row older
than `setTtlSeconds` is dropped, not minted expired.

`POST /ssf/events:emit` and SCIM append and fan out their own row in one transaction (`emitNow`), so a failure leaves
nothing queued and answers 500. Such a row is never seen by a worker, and it is not held behind an older row about
its subject: an inline event's SETs can be queued ahead of an earlier audit or logout event's about the same subject
that is still in the outbox (F-0562).

A batch the store refuses for what an event holds - SQLSTATE class 22 or 23, such as a NUL that text and jsonb cannot
hold - is written one event at a time, and the refused event is dropped with `ssf.set.dropped` `failed` and a WARN
naming its type, source and SQLSTATE; any other store error keeps the batch, as above. So one bad event cannot hold up
the node's hand-off. The fan-out's WARN lines name the failure's class and SQLSTATE, not the database's message, which
for a refused batch INSERT spells out the subject and the signed SET.

`LocalEmissionOutbox` is the in-memory and `ldm` stores' outbox: one lock, the same ordering, and a row that remembers
the streams it has queued for, so a fan-out that fails part way queues each stream once when it is tried again. It is
this node's memory (F-0560). The bridge's 5 s duplicate window stays per node.

Verified 2026-10-07 on JDK 17 against a local PostgreSQL (14.15; CI runs 16): `SsfStoreContract`'s outbox tests on all
three stores; `EmissionOutboxOnPostgresTest` with two `JdbcSsfStore`s on one database - 2,000 events from sixteen
threads about 50 subjects to six streams (two also named alone), four workers per node: one SET per event per stream,
each subject in order by `seq`, no row left; a node that appends and never fans out; a worker that holds a row and
fails after minting while the other node skips it, then one SET per stream; `emitNow` racing the other node's workers;
one logout hint at both nodes; a store that stops (each source call under 50 ms, 50 of 150 dropped `queue_full`, one
`ssf.outbox.write_failed`, the 100 kept written and fanned out when it is back); a SCIM deprovision that reaches the
stream it leaves; V307 to V309 over a queued backlog. `MigratorOnPostgresTest` uses the outbox and the replay table as
the runtime role. The Kafka publisher's registration is tested with a real `Lifecycle`: a worker registered after it
closes first.

Rig `pf-p4-ssf-outbox`, 2026-10-07 (PingFederate 13.1.3, development profile, `tables` store on PostgreSQL 16

## Package S10E: A shared, durable SSF receiver inbox: 202 after commit, retried actions, acknowledgements any node can send

RFC 8935 §2 (fetched from rfc-editor.org, 2026-10-07): "Once the SET has been validated and persisted, the SET
Recipient SHOULD immediately return a response indicating that the SET was successfully delivered. The SET Recipient
SHOULD NOT perform further processing of the SET beyond the required validation steps prior to sending this
response." Before this package the receiver ran every handler before it answered, kept a 10,000-entry `jti` window in
each node's memory, and held the poll's pending acknowledgements in fields that a lost lease forgot. Now
`SsfReceiverService.receive` verifies and admits (`INSERT ... ON CONFLICT (iss, jti) DO NOTHING`) and returns; a
duplicate is answered as the first was (§2: "The SET Recipient MUST respond as it would if the SET had not been
previously received"). The key is `(iss, jti)`, compared bytewise, because RFC 7519 §4.1.7 has "collisions MUST be
prevented among values produced by different issuers as well" and "The "jti" value is a case-sensitive string".

The worker rebuilds each SET from the stored, verified JWS without verifying it again, since the transmitter's keys
may have rotated, and passes the row's issuer to the handlers, so the `iss_sub` mapping (H-SSF-1) is unchanged. A
claim lasts 60 s; a node that dies mid-action leaves its SETs to another worker after that, so a handler can run
twice; the instance registry's handler changes nothing the second time, the grants handler revokes any grant issued
since its first run. On an inbox that is not durable (the in-memory and `ldm`
stores) the handlers still run before the answer, as before. A clustered production node refuses SSF_RECEIVER with an
inbox that is not shared; SSF itself is already refused there on those stores.

The poll acknowledgements need no fence: RFC 8936 §2.4, "The SET Recipient SHOULD accept repeat SETs and acknowledge
the SETs regardless of whether the Recipient believes it has already acknowledged the SETs previously", so a node
that sends acknowledgements and dies before marking them only sends them again.

once, sixteen times - one row, every answer a success, each handler once; a SET pushed again after it was acted on;

moves before its acknowledgements are sent; an inbox that cannot be written. `ReceiverInboxContract` runs on all three
stores, and `MigratorOnPostgresTest` uses the inbox as the runtime role.

## Package T5B: The operator API asks for DPoP nonces, gm-api reads act as rs-validation does, and the attester and the RAR plugin audit what they refuse and decide

Package T5B of Phase 4, wave 1, on branch `prod/p4-operator-tail`, built and verified on 2026-10-05 on JDK 17.

**DPoP nonces (F-0276).** `OperatorAuthenticator` switches on rs-validation's `DpopNonces`: a nonce is an HMAC over
the minute under a 32-byte secret, current for a minute and accepted for one more. RFC 9449 §9 is quoted in the
authenticator's javadoc, and §8 and §8.2 in `docs/operator/operator-authentication.md` (§8: "Nonce values MUST be
unpredictable."). With Redis the secret
is written once under `oidf:admin:dpop-nonce:secret` for a day and every node reads it; a node that cannot read it
answers 503 `nonce_unavailable`. The default is on in every profile and `false` is classed forbidden-in-production:
the Phase 4 plan's decision 1 closes every 0.7.0 finding in Phase 4, and a nonce that a production deployment could
switch off would leave the finding's window open where it matters. `use_dpop_nonce` is reached only with a valid
token and an otherwise valid proof, so it never counts as a failed authentication. `OperatorNonceTest` (Redis
included) pins the round trip, the move to the next nonce, the shared secret and the profile rule.

**gm-api (F-0228, F-0310).** `TokenClaims` calls rs-validation's `ActChain` rather than a copy, so the two cannot drift;
its javadoc no longer names demo-rs's class. rs-validation accepts the legacy string form only when a development
deployment's own code calls `allowLegacyStringAct()` on its validator - a builder call, not a setting - and gm-api has
no code of a deployer's to make that call, so it refuses the string form in every profile: stricter than
rs-validation, never looser. gm-api.war now bundles rs-validation; `PfTokenVerifierTest.theWarLoadsTheOperatorAuthenticator`
loads the authenticator from the war's class path.

**Operator API presence and the static bearer (F-0311, F-0312).** `ComponentSwitches.PRESENCE` for `OPERATOR_API`

the token (through the entry's new `components: [OPERATOR_API]`) rather than FAILED_CONFIG naming the switch.
`ComponentSwitchesTest.theOperatorApiIsPresentOnItsTokenSettingsNotOnTheStaticBearer` pins both.

**The attester's refused clients (F-0336).** `PfIssuanceClientResolver` emits the event from both the index rebuild
and `resolve`. The property and reason are read from the refusal's message by `refusal`, which only ever returns one
of the resolver's property names (or `unnamed`) and one of six fixed reason codes, so a value quoted in a message - an
unsupported evidence type, an instance's subject - never reaches the event. Because the index rebuilds every 30 s,
the last refusal per client is remembered (up to 1,024 clients) and not repeated. The `invalid_client` response still
names the property, as before: it is the client's own configuration and carries no value.

**The RAR plugin's audit route (F-0376).** The PingFederate SDK offers the plugin an audit route:

## Known gaps

The production-readiness review of 2026-09-26 found seven blockers. At 0.7.0, B1 to B3 are closed (0.4.0), B5, B6 and
B7 are closed (F-0005, F-0006, F-0007), and B4 is mitigated ([F-0004](../findings.md#f-0004)).
`python3 tools/findings.py list --status open` lists everything still open (2026-10-09); these are the gaps a
deployment should plan around.

- **The clustering claim is narrow** ([F-0601](../findings.md#f-0601), high, open, 0.8.0;
  [U-0601](../findings.md#u-0601)). Federation, client attestation (the AS side and the attester), automatic
  registration, the SSF receiver, hosting, the operator APIs and FAPI are not verified on a cluster: the reference
  cluster switches them off, so no cross-node challenge, replayed proof, evidence binding or engine-written
  registration ran, and the registration-sweeper, ssf-poll-receiver and federation-key-observer leases were not
  failed over on two nodes. No SSF emission ran during the fault scenarios, and ready stayed 200 through 30 s of
  PostgreSQL loss. Run those components on one node, or test them on your cluster yourself
  (**Run federation, attestation, automatic registration and the SSF receiver on one node, or test them on your cluster
  yourself.**).
- **The `ldm` SSF dialect is single-node** through 1.0.0 (F-0387, F-0535, F-0550, F-0555, F-0560 accepted until
  2027-06-30; F-0540 retargeted to 1.1.0): a clustered production node refuses it.
- **A new engine trusts a private CA only after one restart** ([F-0585](../findings.md#f-0585), medium, 0.8.0).
- **The client storage window**: a disabled client works on the other engines for about a minute (U-0027, PingFederate's).
- **The engine's and the RAR plugin's metrics on a running PingFederate** are unit-tested, not seen on a rig
  ([U-0565](../findings.md#u-0565)); the scrape's JWT bearer grant through an OAuth Assertion Grant connection follows
  PingFederate's documentation and admin API model and has not been driven end to end.
- **gm-api refuses the string-form `act`** this platform's own token-exchange mapping emits, until U-0009 settles
  whether PingFederate can emit the object (T5B).
- **main has no branch protection** ([F-0605](../findings.md#f-0605), medium, 1.0.0): David declined GitHub Pro, and
  the release gate (a green Build and a green licensed run on the tagged commit) is what holds.
- **The other open highs**: [F-0015](../findings.md#f-0015) gm-api's demo URLs in `web.xml` and
  [F-0305](../findings.md#f-0305) device-enrolment key proofs without `iat` (0.9.0).
- **The retargeted findings** above, and the open Phase 4 unverified items: U-0025 (whether an engine receives a key created on the console node), U-0521
  (ten modules guarded for secrets in their logs on start-up and shutdown only), U-0565, U-0580 (a plugin's insecure
  TLS reported by its WARN only) and U-0601, beside U-0009.
- **Three JDKs**: local builds on 20, CI on 17, PingFederate's image on 21 (U-0155).
