# 0.8.0 (2026-11-14) - Phase 5: attestation features complete

0.8.0 is Phase 5 of the production programme: client attestation feature-complete against ABCA draft-11, and the
attester's sources made safe. A client's CIMD document is one per operator-listed client with the operator's trust
roots, the attester signs only with listed transit keys, wallets are trusted only through the trust chain and their
provider's status list, SPIRE is read through a read-only entry reader over mutual TLS, and what a workload proved can
narrow what it is granted. The attester mints `agent_id`s from an agent registry with suspend, reactivate and revoke.
At the authorization server, an attestation can be required to carry Trust Marks and minimum key-storage and
user-authentication levels, can be single use, and is refused at the token endpoint once its instance or agent is
suspended or revoked - checked live, or through a Token Status List the attester and device enrolment publish. A
revocation goes out as CAEP, agent instances are managed over SCIM, and refresh tokens are bound to the client
instance key. The SSF transmitter can tell a receiver when an agent or device instance is registered, when an
attestation is issued or refused, and when the attester's signing key rotates. Every finding targeted at 0.8.0 is closed or retargeted with a dated reason; none is accepted.

**The clustering claim is 0.7.0's, and no wider.** Federation, client attestation, automatic registration, the SSF
receiver and everything 0.8.0 adds to them are not verified on a cluster ([F-0601](../findings.md#f-0601), high,
0.9.0): run them on one node, or test them on your cluster yourself.
[deployment-limits.md](../operator/deployment-limits.md) says what is supported.

**Read "Before you deploy" first.** The items are in package order; [the upgrade
guide](../operator/upgrading/0.7.0-to-0.8.0.md) puts them in the order to do them. The items that stop a deployment
are:

- the migrations - **Run `db-migrate migrate --family agent` and `grants` before deploying if you keep a registry.**
  (A22, V201), **Run the agent family's migrations first.** (E12, V202) and **Migrate the federation family to V107
  first.** (L01B);
- removed settings, each refused by name - **`OIDF_ATTESTER_CIMD_URL` is removed.** (B02B), **Unset
  `OIDF_ATTESTER_SPIRE_ENTRIES_URL` before you upgrade.** (B08) and **Remove `clientAttestationPopMethodsSupported`
  from the federation servlet's init-params.** (E05);
- what production now refuses - **Move inline attester keys to OpenBao.** (B04), **Move off
  `OIDF_WALLET_PROVIDER_JWKS` in production.** (B05), **Set `OIDF_ATTESTER_EXTERNAL_CEILINGS` if you run a federation
  entity or CIMD clients in production.** (B03) and **Give every `OIDF_ENTRA_AGENT_DIRECTORY` entry a `tenant` and
  `instances` in production.** (B10A);
- what is on by default - refresh-token binding (**Expect bound tokens to need an attestation.**, **Expect another
  instance's refresh to fail.** and **Use Redis on a cluster, and keep its keys from being evicted.**, E15) and the
  revocation check once a register is configured (**Turn the check off, or install the filter, in a deployment without
  the token-endpoint filter.**, E11);
- callers that must change - **Use unbound bearer access tokens for GM.** (REVIEWGM), **Keep request bodies within 1
  MiB.** (REVIEWHTTP), **Make sure every iOS client sends the bound nonce.** (REVIEWENROL) and **Send bounded enrolment
  proofs.** (REVIEWPROOF).

The rest ask for a check or a small change, or apply only once you turn a feature on.

## Before you deploy

1. **Follow the upgrade guide, which puts these items in the order to do them.**
   [docs/operator/upgrading/0.7.0-to-0.8.0.md](../operator/upgrading/0.7.0-to-0.8.0.md) starts with the preflight run
   and the three new migrations, and lists every item below by its bold title in upgrade order, grouped by area. The
   numbered items below are in package order, the order the packages' notes were folded in, not the order to do them
   in.
2. **Run federation, attestation, automatic registration and the SSF receiver on one node, or test them on your
   cluster yourself.** (release) 0.8.0 makes 0.7.0's clustering claim and no wider one: the reference cluster still
   switches these components off, so the cluster suite never drove a challenge on one engine and a token on the
   other, a replayed proof or an engine-written registration (F-0601, U-0601, 0.9.0). The same holds for what 0.8.0
   adds to them: the status lists, refresh-token binding, the SCIM endpoint and outbound CAEP were tested on one node.
3. **Run `db-migrate migrate --family agent` and `grants` before deploying if you keep a registry.** (A22) A database the
   agent registry uses needs V201: `java -jar oidf-db-migrate.jar migrate --family agent`, then
   `grants --runtime-role <role> --family agent --apply`, which gives the runtime role SELECT and INSERT only on
   `agent_status_audit_log` ([database-migrations.md](../operator/database-migrations.md)). Without it the
   listener's part of ATTESTATION_ISSUER is FAILED_CONFIG naming the family, and issuance answers 503. On a large
   `agent_identity` table, V201's CHECK constraint and its non-concurrent `CREATE INDEX` lock the table while they
   run, which holds up issuance: apply it in a quiet window.
4. **The agent registry is off unless `OIDF_AGENT_REGISTRY_MODE` is set.** (A22) Unset, the attester behaves as in 0.7.0:
   no `agent_id`, and one INFO line at start-up says the AI Agent Profile §6(2) is not met. Set it to `database` with
   `OIDF_AGENT_REGISTRY_DATA_STORE_ID` naming a PingFederate JDBC data store on PostgreSQL (it may be the authority's)
   to mint `agent_id` on every attestation. `memory` follows the in-memory-state rule: production refuses it without
   `in-memory-state` in `OIDF_ACCEPTED_RISKS`, and always on a clustered node. The default is planned to flip at 1.0,
   with the `sub` change (F-0062).
5. **A storage fault is now 503, not 500.** (A22) A client or monitor that treated the attester's 500 `server_error` from a
   registry fault as permanent should retry the 503 `temporarily_unavailable` instead.
6. **A new operator surface, /federation/attestation/agents.** (A22) Give the operator clients that should use it the
   exclusive scopes `oidf.admin.agents.read` (look up, list, audit) and `oidf.admin.agents` (suspend, reactivate,
   revoke) in PingFederate ([operator-authentication.md](../operator/operator-authentication.md)). A record shows
   the workload's `instance_subject` beside its `agent_id`, to operators only. Reasons are kept in the audit log and
   the event: name an incident or a ticket, never a person. Never grant `oidf.admin.agents` to an agent's own client:
   nothing in the attester stops a token holding it from reactivating its own agent.
7. **Install PyYAML before running `tools/profile.py`.** (AGENTIC-IDP-PROFILES) It is the tool's one dependency outside Python's standard
   library, hash-pinned in `tools/profile/requirements.txt`:
   `python3 -m pip install --require-hashes -r tools/profile/requirements.txt`, in a venv where the system Python is
   externally managed. `render` and `check` also need `terraform` on `PATH` (or `--no-terraform`, which leaves out
   the Terraform env output and the root's validations), and `author` needs Docker and Terraform.
8. **Name a conformance profile with `PF_PROFILE`.** (AGENTIC-IDP-PROFILES) `conformance/up.sh` keeps its interface. `PF_PROFILE` takes
   `federation`, `federation-op`, `attester-cimd`, `ciba-ping` (new) or `fapi2-attestation` (X-E09), each picking `profiles/conformance-<value>.yaml`;
   unset is `conformance-fapi2`, which the FAPI 2.0, FAPI-CIBA (poll) and SSF plans share. And
   `PF_HARNESS=1` adds `conformance-federation-harness` over it. A rig variable you set in `conformance/vars.env` or
   a `vars.*.env` file goes in that profile's `env` block, or a profile of your own that extends it.
9. **Move Terraform you applied from `conformance/terraform` or `reference/terraform`.** (AGENTIC-IDP-PROFILES) Both are gone, and so is
   their state's meaning: the rig and the stacks author with fresh state on every run. A deployment that applied one
   of them writes a profile (start from `minimal` or the preset nearest it), runs `check`, and authors its archive
   with `tools/profile.py author`.
10. **Move a CIMD document to OIDF_CIMD_CLIENTS before upgrading.** (B02A) `OIDF_ATTESTER_CIMD_URL` no longer does anything
    in any profile: clients that only its document described cannot be issued attestations after the upgrade. List each client in
    `OIDF_CIMD_CLIENTS`, keyed by its Client Identifier URL (https, a path, no query or fragment), with its
    `issuer`, `trust_root`, `subject_prefixes` and optional `evidence_type`, `max_issued_ttl` and `signing_key_ref`;
    put the trust roots in `OIDF_CIMD_TRUST_BUNDLES`; publish one document per client at its URL whose `client_id` is
    that URL; and unset `OIDF_ATTESTER_CIMD_URL`. The client id becomes the URL, so the PingFederate client is
    registered under it. No configuration in this repository, pf-oidf-modules or idp-agentic-demo set the old
    variable (checked 2026-10-08); a converter for the old document comes with B02B.
11. **Take trust roots, issuers and keys out of CIMD documents.** (B02A) A document that carries `instance_trust`, or in its
    `oauth_client_attestation` object or an instance any of `bundle`, `bundle_url`, `spiffe_trust_bundle`,
    `wallet_providers`, `trust_domain`, `evidence_type`, `evidence_issuer`, `issuer`, `signing_jwk` or
    `signing_key_ref`, is refused and its client dropped, as is one with a shared secret or a private key anywhere in
    it. The operator gives all of those in `OIDF_CIMD_CLIENTS` and `OIDF_CIMD_TRUST_BUNDLES`.
12. **Keep each CIMD document under 5 KiB, or raise the cap.** (B02A) A document over `OIDF_CIMD_MAX_BYTES` (5120 by
    default, the CIMD draft's recommendation; up to 65536) is a failed fetch. A client with many instances may need a
    wildcard instance (`spiffe://.../payments/*`) or a higher cap.
13. **Serve each document from a public https address.** (B02A) The fetch has no exemption from the outbound rules: a host
    that resolves to a private or special-use address is refused. In development a host named in
    `OIDF_FETCH_HOST_ALLOWLIST` is exempt; in production the allow-list does not apply to these fetches (CIMD -02
    §8.6: the exception "MUST NOT" apply in production deployments), so a production CIMD host must be public.
    Redirects are not followed, and only a 200 with a JSON content type is read.
14. **`OIDF_ATTESTER_CIMD_URL` is removed.** (B02B) Set to anything not blank (or `oidf.attester.cimd.url`), the attester
    does not start in any profile, and server.log and the preflight say `OIDF_ATTESTER_CIMD_URL was removed in 0.8.0;
    set OIDF_CIMD_CLIENTS instead`. Run the preflight before upgrading; if it names the variable, follow the CIMD
    section of the upgrade guide and unset it. No configuration in this repository, pf-oidf-modules or
    idp-agentic-demo sets it (checked 2026-10-09, U-0615).
15. **Convert with `tools/cimd-split.py`.** (B02B) It reads the old document from a file and writes one document per client,
    `oidf-cimd-clients.json` and `oidf-cimd-trust-bundles.json`. The trust roots are written only with
    `--accept-bundles`, after you have confirmed the printed thumbprints with each trust domain's owner; without it
    they read `"jwks": "REVIEW"` and the tool exits 3. Review each client's `subject_prefixes`. An entry with
    `signing_jwk` stops the tool: move that key to OpenBao and name it with `signing_key_ref`. So does a private
    key anywhere else in an entry, since each document is published at its client's URL. The tool is not in the
    public repository; ask for it if you deploy from there.
16. **CIMD client ids become their URLs.** (B02B) Each converted client is renamed to the URL its document is served at
    (CAS §6.2). Register it in PingFederate under the new id and rename its `OIDF_BRIDGE_SIGNING_KEYS` entry,
    keeping its `attesters`; the tool prints the rename table.
17. **Set `OIDF_ATTESTER_EXTERNAL_CEILINGS` if you run a federation entity or CIMD clients in production.** (B03) Without
    it every one of their clients is refused. Give each client, or `"*"`, the widest `authorization_details` you
    will grant; the [upgrade guide](../operator/upgrading/0.7.0-to-0.8.0.md#external-ceilings) has the steps. A
    value the RAR models refuse stops the attester at deploy (`FAILED_CONFIG`), naming the client id.
18. **Merge a client's federation instances under one `client_id`.** (B03) Before 0.8.0 the second entry for a client never
    matched, so an entity that worked around it with one client id per instance can now list them under one.
19. **Move inline attester keys to OpenBao.** (B04) Under the production profile `attestation_signing_jwk` refuses its
    client (the attester skips it with `attestation.issuer.client_refused`, `property` `attestation_signing_jwk`, and
    the others keep issuing), and `OIDF_ATTESTER_SIGNING_JWK` set refuses the whole attester at the start-up audit.
    Import or create the key in OpenBao transit (`ecdsa-p256`, `-p384` or `-p521`) and set
    `attestation_signing_key_ref`. A demo rig that keeps an inline key sets `OIDF_DEPLOYMENT_PROFILE=development`;
    pf-oidf-modules' inline demo client (`attestation-demo-clients.tf`) is one.
20. **List your transit keys in `OIDF_ATTESTER_SIGNING_KEYS` with the issuers they sign for.** (B04) In production every
    key ref a client names must be a member, and the client's `attestation_issuer` one of that member's `issuers`:
    `{"attestation-es256": {"issuers": ["https://attester.example.com"]}}`. Without it every client that names a key
    ref is refused and the `AttesterSigningKeys` part is `DEGRADED`. A value that is not key names to https issuers
    is `FAILED_CONFIG` at deploy. Find your clients with `git grep attestation_signing_key_ref` over your PingFederate
    configuration, or from the `attestation.issuer.signing_key_refused` events after deploying to staging.
21. **Set `OIDF_ATTESTER_SIGNING_KEY_REF` for federation clients.** (B04) It replaces `OIDF_ATTESTER_SIGNING_JWK`
    for the clients an `OIDF_ATTESTER_FEDERATION_ENTITY` describes, and must be listed in `OIDF_ATTESTER_SIGNING_KEYS`
    for each of their issuers. A CIMD client signs with its `OIDF_CIMD_CLIENTS` `signing_key_ref`, else this key, under the
    same allow-list (B02A).
22. **Federation entries may no longer name a signing key.** (B04) An entry in a federation entity's
    `spiffe_client_bindings` that carries `signing_key_ref` or `signing_jwk` refuses that client, with a WARN naming it
    and `attestation.issuer.signing_key_refused` (`rule` `entry_names_key`); its siblings keep issuing. Remove the
    member from the entity statement.
23. **Give the attester's OpenBao token a policy limited to its own keys.** (B04) The attester and the hosted agents read
    the same `OIDF_OPENBAO_TOKEN`, so the allow-list is enforced by the attester, not by the vault. A policy allowing
    `read` on `transit/keys/<key>` and `update` on `transit/sign/<key>` for the listed keys only is in the attester's
    README, "Signing keys".
24. **Do not rotate a federation-published attester key in place.** (B04) `OIDF_FEDERATION_ATTESTER_JWKS` is read at start,
    so a key rotated in OpenBao signs with a `kid` verifiers have not been given until PingFederate restarts. Create a
    new key, publish and list it, restart, then switch clients to it (the attester's README, "Rotating the attester's
    signing key").
25. **Pin every wallet client's provider.** (B05) A client whose `attestation_evidence` is `wallet-instance-attestation`
    now needs `attestation_trust_domain` set to the entity id of the one wallet provider it accepts. Without it the
    client is refused at load (`invalid_client`; the `attestation.issuer.client_refused` event names
    `attestation_trust_domain`, reason `missing`) and the attester skips it.
26. **Publish wallet provider keys in `openid_wallet_provider.jwks`.** (B05) A provider's WIA-signing keys must sit in
    `metadata.openid_wallet_provider.jwks` of its resolved metadata, each with a `kid`, `use` `sig` or none. A
    provider that published only its federation `jwks`, or `oauth_client_attester.jwks`, or its keys by `jwks_uri`, is
    refused, and so is every WIA it issues.
27. **Check your wallets' `typ`.** (B05) A WIA needs `typ: oauth-client-attestation+jwt` unless
    `OIDF_WALLET_ATTESTATION_TYPES` lists its type. A WIA with no `typ`, or with `wallet-instance-attestation+jwt`,
    `wallet-attestation+jwt` or `wallet-unit-attestation+jwt`, was accepted before; list the value to keep accepting
    it. Refusals are counted under `check="typ"`.
28. **Move off `OIDF_WALLET_PROVIDER_JWKS` in production.** (B05) The start-up audit now refuses `ATTESTATION_ISSUER` in the
    production profile while it is set. Trust wallet providers through the federation (`OIDF_ATTESTER_OP_ISSUER` with
    the trust controller and its pinned anchor keys). In development, an entry that is not a JWK Set of public keys
    is `FAILED_CONFIG` at deploy, where it was skipped.
29. **Expect new wallet `agent_id`s.** (B05) The agent registry keys a wallet on its provider and the thumbprint of its bound
    key, not on the WIA's `sub`, which certified wallets share across every copy. Every wallet instance gets a new
    `agent_id` at its next issuance, and anything that recorded the old one must re-register it.
30. **Open egress from the attester to your wallet providers' status list hosts.** (B06) A WIA that carries `status` now
    makes the attester GET the list at its `uri`, under the federation's outbound rules (`OIDF_FETCH_*`: https only and
    no private address in production), following at most three redirects. A host the PingFederate nodes cannot reach
    means every WIA pointing to it is answered 503 until it answers. Watch
    `oidf_attester_wallet_status_fetches_total{result}` for anything but `ok`.
31. **Expect 503 while a status list is unreachable.** (B06) There is no stale grace by default: once a cached list is past
    its freshness (its `ttl` clamped to 60-3600 s, and never past its `exp`) and a refetch fails, the WIA is refused
    503 `temporarily_unavailable`. If a provider's list host is flaky, set `OIDF_WALLET_STATUS_STALE_GRACE` (at most
    900 s); each second of grace is a second longer a revocation can go unseen.
32. **Decide which wallet providers must carry `status`.** (B06) By default a WIA without `status` is still accepted. List
    the providers whose WIAs must point to a status list in `OIDF_WALLET_STATUS_REQUIRED_PROVIDERS` (entity ids,
    comma-separated, or `*`); a WIA from one of them without `status` is then refused.
33. **Review the new size settings.** (B06) `OIDF_WALLET_STATUS_MAX_BYTES` (response body, 1 MiB),
    `OIDF_WALLET_STATUS_MAX_LIST_BYTES` (inflated list, 16 MiB) and `OIDF_WALLET_STATUS_CACHE_MAX_BYTES` (all cached
    lists on a node, 64 MiB, never below the list cap) bound the heap the check can use. A provider whose list is
    larger than a cap is answered 503 for every WIA pointing to it. `OIDF_WALLET_STATUS_TTL_MIN` and
    `OIDF_WALLET_STATUS_TTL_MAX` clamp how long a list is trusted. A value out of range, or a TTL minimum above the
    maximum, is `FAILED_CONFIG` at deploy, naming the setting.
34. **Unset `OIDF_ATTESTER_SPIRE_ENTRIES_URL` before you upgrade.** (B08) A deployment that still sets it, in any profile,
    fails to start the attester: `ATTESTATION_ISSUER` is refused, the start-up audit names the setting and its
    replacement, and `/federation/attestation` answers 503.
35. **Deploy the SPIRE entry reader and set the reader settings to keep SPIRE selectors.** (B08) Run
    `services/spire-entry-reader` beside SPIRE Server, then set
    `OIDF_ATTESTER_SPIRE_READER_URL` (https), `_TRUST_DOMAIN`, `_CA_FILE` and `_CLIENT_KEY_PAIR`
    (attester README, SPIRE). Unset, the attester reads no SPIRE
    selectors and behaves as before for everything else.
36. **Create the PingFederate SSL client key pair and give its public key to the reader.** (B08) In the admin console, create
    an SSL client key pair, name its alias in `OIDF_ATTESTER_SPIRE_READER_CLIENT_KEY_PAIR`, and add its SPKI to the
    reader's allowed clients. Under the production profile an alias PingFederate does not have refuses
    `ATTESTATION_ISSUER` at start. A rotated key pair is picked up within 60 s, without a restart.
37. **Move any policy off `workload.attributes.selectors` and `.spire`.** (B08) Signed attestations no longer carry them. A
    relying party, token mapping or policy that read them gets nothing there now; it should never have conditioned on
    them, since nothing authenticated the old endpoint. Selector-conditioned ceilings belong in the attester and arrive
    with B09.
38. **Choose the failure mode.** (B08) With the reader set, a `spiffe-jwt` workload SPIRE has no entry for, or whose SPIFFE
    ID is outside the reader's trust domain, is refused 403 `instance_not_authorized` in either mode: one reader and one
    trust domain per deployment. When the reader cannot be read (down, TLS, a malformed or inconsistent answer, too
    many entries), `closed`, the default, refuses 503 `temporarily_unavailable`, and `downscope` issues without
    `spire:` selectors and emits the audited `attestation.spire.downscoped`. Under `closed`, a SPIFFE workload's
    issuance now depends on the reader being up. The
    [upgrade guide](../operator/upgrading/0.7.0-to-0.8.0.md#spire) has the steps.
39. **Send `asserted_context` on every request to a client that names a resolver.** (B10A) A client with
    `attestation_asserted_context_resolver` set now refuses 400 `invalid_request` ("asserted_context is required for
    this client") any request without it, and one whose `asserted_context` is not
    `{"type": "entra-agent-id", "value": "<oid>"}` with a string value of 1-256 characters. Before, such a request was
    minted the evidenced ceiling unnarrowed. Check each caller of such a client sends it, as a JSON string.
40. **Stop sending `asserted_context` to clients that name no resolver.** (B10A) It used to be ignored; it is now refused 400
    `invalid_request`, so a caller never believes it was narrowed when it was not. Search your callers for the field
    and either drop it or opt the client in.
41. **Give every `OIDF_ENTRA_AGENT_DIRECTORY` entry a `tenant` and `instances` in production.** (B10A) Each entry needs
    `tenant` (the Entra tenant GUID the evidence's `tid` must equal) and `instances` (the instance subjects or Azure
    object ids allowed to assert that oid) under the production profile, and may add `evidence_types` (default
    `["azure-mi-token","aks-sa-token"]`). Without `instances`, any opted-in client's workload in the tenant could assert
    the agent; development still accepts an entry without them. A directory that is not a JSON object of objects, carries an unknown member, a non-string `display_name`,
    lists that are not lists of strings, an unsupported evidence type, a `tenant` that is not a GUID or a `ceiling` the
    containment models refuse now makes the issuance part `FAILED_CONFIG` at deploy, naming the setting and the entry;
    before, such a directory or entry was dropped without a word. AKS service-account evidence proves no tenant, so it
    can assert an agent only through a development entry with no `tenant`.
42. **Check PingFederate clients that already had `attestation_asserted_context_resolver` set.** (B10A) The property used to
    have no effect on a PingFederate client, so those clients were minted their whole evidenced ceiling. From this
    release it takes effect: their callers must send `asserted_context` (above), and the resolver must be registered,
    or the client is refused at load (`attestation.issuer.client_refused`, property
    `attestation_asserted_context_resolver`, reason `refused`) and its requests `invalid_client`. Apply the regenerated
    `docs/extended-properties.json` to your PingFederate before setting `attestation_asserted_context_policy`, which is
    reserved and refused for now.
43. **Check `challengeEndpointEnabled` before you rely on the attester's challenge endpoint.** (B11A) The issuance servlet's
    init-param now decides both whether the endpoint serves and whether the metadata advertises it. If it is
    `challengeEndpointEnabled=false`, `/federation/attestation/challenge` now answers 404 and workloads that still fetch
    challenges from it fail. Remove the init-param if they need it. With `challengeRequired=true` as well, no issuance
    can succeed.
44. **Set `challengeEndpointEnabled=false` on the issuance servlet if you set it on the metadata servlet alone.** (B11A) Before
    0.8.0 that hid the endpoint from the metadata while it still served. The metadata servlet's value is no longer read
    once the issuance servlet has started, and the issuance servlet's defaults to `true`, so such a deployment now
    advertises the endpoint and serves it. To keep it off, set the init-param on the issuance servlet.
45. **Check combined-mode clients for `use_attestation_challenge`.** (E02) A client that authenticates with a DPoP proof in
    place of the PoP, and retries on `use_attestation_challenge`, now gets `use_dpop_nonce` instead, with the nonce to
    use in the `DPoP-Nonce` header. A client built on a DPoP library already handles this. A hand-written one should
    retry once on either code, using the header's value.
46. **Review the challenge cap if refusals are frequent.** (E02) Each `use_attestation_challenge` or `use_dpop_nonce` refusal
    now writes a challenge and counts against the caller's challenge cap (60 per 60 seconds by default), the same cap
    the challenge endpoint uses. A client that is refused often can reach the cap sooner and then gets the refusal
    without a header. `attestation.challenge.refused` with `reason=rate_limited` and `via=error` shows when that happens.
47. **Keep PingFederate's DPoP nonce requirement off with attestation combined mode.** (E02B) The filter answers
    `use_dpop_nonce` with a nonce from its own challenge store and forwards the `DPoP` header to PingFederate as it
    came. If PingFederate's `dpop_proof_require_nonce` is also on (the profile's `fapi2.dpop_require_nonce`), each side
    refuses the other's nonce and a DPoP client loops. It is off by default; check that no environment turns it on.
48. **Check your required-claim names.** (E03) A name no attestation carries now refuses every request that needs it, with
    `insufficient_disclosure`. Before upgrading, compare `OIDF_ATTESTATION_REQUIRED_CLAIMS` and each client's
    `attestation_required_claims` with the claims your attesters mint; after it, the filter's start-up log lists each
    global name and the check it gets.
49. **Clients that branch on `invalid_client`.** (E03) A client or monitor that treats `invalid_client` as "unknown client"
    and anything else as retryable will now see `invalid_client_attestation` for a bad attestation or proof. Both are
    401 and neither is retryable without a new attestation or proof.
50. **Remove `clientAttestationPopMethodsSupported` from the federation servlet's init-params.** (E05) It is a removed name
    from 0.8.0, and the federation servlet does not start while it is set. Nothing replaces it: no document carries the
    member any more.
51. **Check any algorithm list you set on the federation servlet.** (E05) `clientAttestationSigningAlgValuesSupported`,
    `clientAttestationPopSigningAlgValuesSupported` and `dpopSigningAlgValuesSupported` used to be advertised only. They
    now also decide which algorithms the token endpoint accepts, so a client signing with an algorithm left off the
    list is refused. The defaults accept what was accepted before. A list naming `none`, a MAC such as `HS256` or a JWE
    algorithm stops the federation servlet starting, naming the setting.
52. **If you set `attestationSigningAlgValuesSupported`, make it name your attester keys' algorithms, on the issuance
    servlet.** (E05) Unset, nothing needs doing: the documents advertise what your keys sign with, `EdDSA` or `ES384`
    included. Set, the list is now enforced, so an attester whose key signs with an algorithm it leaves out refuses
    every issuance with `server_error`. If you set it on the CAS metadata servlet alone, it no longer has any effect
    there; set it on the issuance servlet, or remove it.
53. **Expect 404 from `/federation/attestation-challenge` if you set `attestationChallengeEndpointEnabled=false`.** (E05)
    Clients that fetch a challenge there must take it from the token endpoint's `use_attestation_challenge` or
    `use_dpop_nonce` refusal instead, as ABCA-11 §6.1 lets them.
54. **Expect no attestation members while `ATTESTATION_AUTH` is not serving.** (E05) Check its state in the health output if
    a client stops finding `attest_jwt_client_auth` or `challenge_endpoint` in the discovery documents. Before, the
    members stayed while the filter refused the requests they described.
55. **Declare `attestation_single_use` before setting it.** (E06) PingFederate drops an extended property it has not
    declared. The rig's Terraform reads `docs/extended-properties.json` and declares it on the next apply. A
    deployment that declares extended properties some other way adds `attestation_single_use` there.
56. **Raise the attester's issuance limit before turning single use on.** (E06) Each request a single-use client
    authenticates then costs an issuance call to the attester, two for a PAR followed by its token request, and
    `OIDF_ATTESTER_ISSUANCE_REQUESTS_PER_MINUTE` (60 by default) limits those per caller. Above it the attester
    answers 429, and the client gets no fresh attestation and so no token. Set it to at least the request rate of
    the busiest single-use caller.
57. **Declare `attestation_required_trust_marks` before setting it.** (E07) PingFederate drops an extended property it has
    not declared. The rig's Terraform reads `docs/extended-properties.json` and declares it on the next apply. A
    deployment that declares extended properties some other way adds `attestation_required_trust_marks` there.
58. **Check that your attesters carry the marks before you require them.** (E07) Each attester's Entity Configuration must
    list the mark in `trust_marks`, and the Trust Anchor's `trust_mark_issuers` must name its issuer for the type. A
    type no attester holds, or a misspelt one, refuses every attestation, and the refusal event names the missing
    types.
59. **Declare the two extended properties before setting them.** (E08) PingFederate drops an extended property it has not
    declared. The rig's Terraform reads `docs/extended-properties.json` and declares `attestation_min_key_storage` and
    `attestation_min_user_authentication` on the next apply. A deployment that declares extended properties some
    other way adds them there.
60. **Check what your attesters assert before setting a minimum.** (E08) The device attester asserts
    `iso_18045_moderate` for both claims with App Attest evidence, `iso_18045_moderate` key storage and
    `iso_18045_basic` or `iso_18045_moderate` user authentication with PIV, and neither claim for a self-asserted
    device. The workload attester asserts neither. A minimum refuses every attestation without the claim, so a
    server-wide minimum refuses every workload client.
61. **Expect suspended and revoked agents to be refused at the token endpoint once the agent registry is on.** (E11) With
    `OIDF_AGENT_REGISTRY_MODE` set to `memory` or `database`, `OIDF_CLIENT_REVOCATION_MODE` is `live` unless you set it:
    an agent an operator suspended or revoked stops getting tokens at its next request, not when its attestation
    expires. Set `OIDF_CLIENT_REVOCATION_MODE=off` to keep 0.7.0's behaviour; under production that also needs
    `client-revocation-off` in `OIDF_ACCEPTED_RISKS`, or ATTESTATION_AUTH is refused. A deployment with neither register
    configured sees no change.
62. **Revoking does not withdraw tokens already issued.** (E11) A suspended or revoked instance is refused at its next
    authentication, but every access token it already holds stays valid until it expires, up to the access-token
    lifetime, and a resource server that does not introspect keeps honouring it (F-0772, open, X-E13). Keep access-token
    lifetimes short where that matters. A refresh token issued to an attested request is bound to the instance key and
    needs an attestation to redeem (X-E15) unless `OIDF_ATTESTATION_REFRESH_BINDING=off`; set `attestation_required` on
    the clients the instances use so that tokens issued without one are covered too.
63. **Know which requests the check covers.** (E11) It runs only for a request that carries an attestation. A client that
    also has a PingFederate client secret or JWKS, and is not `attestation_required`, can authenticate without one and
    skips the check; set `attestation_required=true` on the clients the registers are meant to govern.
64. **Name the device-instance registry to check device instances.** (E11) Set `OIDF_INSTANCE_REGISTRY_DATA_STORE_ID` to a
    PingFederate JDBC data store on the Identity Object Model's PostgreSQL, the database device-enrolment enrols into,
    with the model's agent-instance migrations applied (`idm.schema_migration`). Its runtime user needs to read
    `idm.entry`, and, for the operator API, the rights device-enrolment's user has to change an instance's status and
    write its ledger entry. A store
    that cannot be reached leaves ATTESTATION_AUTH's `InstanceRegistryListener` part FAILED_DEPENDENCY, retried, and
    every attested request 503 until it starts.
65. **Plan for 503 when a register is down.** (E11) The check fails closed: a register that cannot be read refuses attested
    requests with 503 `temporarily_unavailable`, in production and by default in development. Watch
    `oidf_client_revocation_checks_total{status="unavailable"}`. Development can set
    `OIDF_CLIENT_REVOCATION_FAIL_OPEN=true` to go on with a WARN; production ignores it.
66. **Turn the check off, or install the filter, in a deployment without the token-endpoint filter.** (E11) Where only the OGNL
    issuance criterion verifies attestations, a configured register makes every attested token refused once the check
    applies, active clients included, because the criterion cannot read the registers. Start-up does not refuse this
    setup, because it cannot see it; the first refused token logs one line naming `OIDF_CLIENT_REVOCATION_MODE` and the
    filter, ERROR under production and WARN under development, so search `server.log` for it after deploying. Set
    `OIDF_CLIENT_REVOCATION_MODE=off` (with `client-revocation-off` accepted under production) to go on issuing without
    the check, set `status_list`, which the criterion can check because the list is fetched over HTTP (X-E12), or map
    `ClientAttestationAuthFilter` (the shipped `filters.xml` does).
67. **Grant the new operator scopes only to operator clients.** (E11) Give `oidf.admin.instances.read` and
    `oidf.admin.instances` to the operator clients that should manage device instances
    ([operator-authentication.md](../operator/operator-authentication.md)), never to a device instance's own client.
68. **Run the agent family's migrations first.** (E12) Run `oidf-db-migrate.jar migrate --family agent` before you deploy. V202 adds `agent_identity.status_idx` and
    backfills every existing agent. An attester running against an agent schema that is behind this release is refused,
    as with every agent migration. A node from the previous release still running during a rolling upgrade can still
    insert agents; such an agent is given its index when it is next attested.
69. **Turn the lists on before the verifier mode.** (E12) Nothing is published or checked unless you set `OIDF_ATTESTER_STATUS_LIST_URL` or `ENROLMENT_STATUS_LIST_URL`, and
    `OIDF_CLIENT_REVOCATION_MODE=status_list` or `both` (or a client's `attestation_revocation_mode`). Turn the lists on
    first. Then wait for every attestation minted before that to expire. Only then turn the verifier mode on, because it
    refuses an attestation without a `status` claim.
70. **Make the list URL reachable from every verifier.** (E12) The list URL must reach the endpoint that serves it, and verifiers must be able to fetch it under their outbound rules
    (`OIDF_FETCH_*`: https, and no private address under production).
71. **Give the attester's list a governed signing key.** (E12) Under production the attester's list needs `OIDF_ATTESTER_SIGNING_KEY_REF`, and `OIDF_ATTESTER_SIGNING_KEYS` must
    list each attester issuer for that key. Otherwise the list answers 503 and verifiers in `status_list` mode refuse.
72. **Expect a status-list revocation to arrive late.** (E12) A revocation reaches a verifier in `status_list` mode up to the list's `ttl` later (clamped by the verifier's
    `OIDF_CLIENT_REVOCATION_STATUS_TTL_MIN` and `_TTL_MAX`), plus up to 5 seconds. Use `live` or `both` where the registers
    can be read and that delay matters.
73. **Extension authors: `StatusListClient` moved.** (E12) B06's `StatusListClient` moved from `com.pingidentity.ps.oidf.issuer` in attestation-issuer
    to `com.pingidentity.ps.oidf.jose.status` in oidf-jose:
    - its limits are now read by the caller and passed in (`Limits.checked`), and it counts fetches in a counter the
      caller supplies;
    - `AgentIdentity` gains a `statusIdx` component; the ten-argument constructor is kept;
    - `InstanceRegistry` gains `statusIndex` and `statusListEntries`, and `AgentRegistry` gains `statusIndex`,
      `statusListEntries` and `issuers`, all as default methods.
74. **Decide whether to turn it on.** (E13) Nothing changes unless you set `OIDF_CLIENT_REVOCATION_CAEP=true`.
75. **Run the transmitter beside the registers.** (E13) The setting needs the SSF transmitter in the same webapp as the
    registers. In this repo's image the `pf-runtime.war` merge provides that. The device-enrolment service runs in its
    own process with no transmitter, so a revocation it makes raises no SET.
76. **Make receivers hear the subject.** (E13) Either add `{"format": "opaque", "id": "<agent_id>"}` to their streams, or set
    `default_subjects` to `ALL`. They must also request the event types: `session-revoked`, `account-disabled` and
    `account-enabled`.
77. **Give peers one identifier for both roles.** (E13) The loop guard matches a stream's `aud` against the inbound SET's
    `iss`, so it only works when a peer that both sends to us and receives from us uses the same value for each. For a
    peer that runs this platform, set its `OIDF_SSF_RECEIVER_AUDIENCE` equal to its `OIDF_SSF_ISSUER`. There is no
    exact alternative: nothing links the stream a SET arrived on to the peer's streams here. If the values differ, the
    peer gets its own change back, counted as `emitted`. That changes nothing at the peer, because it already made the
    move.
78. **Watch for unsent SETs.** (E13) The SET is minted on the thread that made the change, after the change commits. A SET
    that cannot be minted is reported as `set_suppressed` with reason `failed`, plus a WARN, and is not tried again. The
    register's change stands, and the token endpoint refuses the agent regardless (X-E11).
79. **Grant `oidf.admin.scim` to provisioning clients only.** (E14) A token that holds it can reactivate any suspended
    instance in either register, including the instance the token's own client runs as. The only control is that
    PingFederate gives the scope to operator or provisioning clients alone. Give a provisioner that only reads
    `oidf.admin.scim.read`.
80. **Declare the new extended property.** (E15) Add `attestation_refresh_binding` to PingFederate's extended properties, as
    `docs/extended-properties.json` lists it, before you set it on a client. PingFederate drops an undeclared property
    without a word, and the client then follows the server's setting.
81. **Expect another instance's refresh to fail.** (E15) An agent platform or app that shares refresh tokens between instances
    of one client, or that rotates its instance key and keeps the old refresh token, gets 400 `invalid_grant` on the
    refresh and has to start a new grant. Refresh with the instance key the token was issued to, or start a new grant
    after a key change.
82. **Expect bound tokens to need an attestation.** (E15) A client that has a client secret or JWKS as well as attestation
    gets 400 `invalid_grant` if it refreshes a bound token without the attestation headers. Before this release that
    refresh worked.
83. **Use Redis on a cluster, and keep its keys from being evicted.** (E15) Bindings are kept with the challenges and the
    replay cache. Without `OIDF_REDIS_URL` they are in one node's memory: a refresh that lands on another node, or comes
    after a restart, finds no binding. Under `on` that refresh is let through (counted as `unknown_allowed`). Under
    `strict` it is refused. Production already refuses in-memory attestation state on a clustered node. The in-memory
    store also refuses new tokens (503) once it holds 65536 live bindings. In Redis, a `maxmemory-policy` of
    `allkeys-lru` or `allkeys-random` can evict a binding, which then reads as unknown: use `noeviction` or a
    `volatile-*` policy with headroom.
84. **Turn on `strict` only after the old tokens are gone.** (E15) Under `on`, refresh tokens issued before 0.8.0 still work.
    Watch `oidf_attestation_refresh_binding_total{action="refresh",outcome="unknown_allowed"}` fall to zero, then set
    `OIDF_ATTESTATION_REFRESH_BINDING=strict`, or `attestation_refresh_binding=strict` on one client at a time. Under
    `strict` a refresh token with no binding is refused 400 `invalid_grant`, and the client has to start a new grant.
85. **Keep bindings at least as long as the refresh tokens.** (E15) Each binding expires with its grant as PingFederate's
    `AccessGrantManager` reports it. A grant with no expiry is kept for `OIDF_ATTESTATION_REFRESH_BINDING_TTL_SECONDS`
    (365 days). Set that at least as long as the longest refresh-token lifetime you issue: after a binding expires, its
    token has no binding.
86. **Plan for 503 when Redis is down.** (E15) A refresh is refused 503 when its binding cannot be read. A token response is
    withheld, and its grant revoked, when the new token's binding cannot be written. Watch
    `oidf_attestation_refresh_binding_total{outcome="unavailable"}`.
87. **Keep rotated-out tokens bound through PingFederate's grace period.** (E15) Leave
    `OIDF_ATTESTATION_REFRESH_BINDING_GRACE_SECONDS` unset, and an old token stays bound until its grant lapses. If you
    set it, make it no shorter than the longest refresh-token rolling grace period in PingFederate, the server's or any
    client's. Otherwise, for the rest of that period, the old token is let through under `on` with any instance key.
88. **Know that only the token-endpoint filter binds.** (E15) A deployment where only the OGNL issuance criterion verifies
    attestations, with no `ClientAttestationAuthFilter` mapped, gets no refresh-token binding at all. The shipped
    `filters.xml` maps the filter.
89. **Accept the risk to turn it off.** (E15) `OIDF_ATTESTATION_REFRESH_BINDING=off` keeps 0.7.0's behaviour. Under production
   it also needs `refresh-binding-off` in `OIDF_ACCEPTED_RISKS`, or ATTESTATION_AUTH is refused.
90. **Turn off `fapi2.dpop_require_nonce` in a profile that also runs the attestation filter.** (F0732) Such a profile now
    fails `python3 tools/profile.py check` (and `render` and `author`) with a problem naming
    `features.fapi2.dpop_require_nonce` and `features.attestation.auth`. Remove `dpop_require_nonce` (it is off by
    default): the filter issues combined mode's nonce. No shipped profile turns both on. A PingFederate configured
    outside the profile tool is not checked; keep its `dpop_proof_require_nonce` off where the filter runs.
91. **Give your policy engine a policy for the new action names before you list them.** (L01A) The seven new decision points
    are off unless `OIDF_PDP_DECISION_POINTS` names them, so nothing changes on upgrade. A PDP that knows only the four
    older action names (`federation.register.explicit`, `federation.register.automatic`,
    `federation.hosted_entity.enrol`, `federation.token.issue`) will answer the new ones by its default - check what that
    is before you list `hosted_entity_reactivate`, `hosted_entity_rekey`, `trust_mark_grant`, `trust_mark_issue` or
    `resolve`, which a denial or no decision stops. Prefer `trust_mark_grant` to `trust_mark_issue`: the Trust Mark
    endpoint is public, and listing the second puts the engine in its path.
92. **Declare the two per-client properties in PingFederate before you set them.** (L01A) `federation_pdp_token_issuance` and
    `federation_pdp_fail_open` are in [docs/extended-properties.json](../extended-properties.json); PingFederate drops
    an extended property it has not been told about, silently. A value other than `true` or `false` in lower case,
    `federation_pdp_fail_open=true`, or `federation_pdp_token_issuance=true` without `OIDF_PDP_MODE=authzen` refuses
    every token for that client.
93. **Expect a renewal to keep what you set on a federation client.** (L01A) Before 0.8.0 an automatic or explicit renewal
    rebuilt every extended property from the relying party's metadata, so an `attestation_*` or `trust_chain_*` value
    an operator set by hand was lost at the next renewal. It is now kept. If you relied on a renewal clearing one,
    clear it yourself.
94. **Leave consuming historical keys off unless you need it.** (L01A) `OIDF_FEDERATION_HISTORICAL_KEYS_CONSUME` is separate
    from `OIDF_FEDERATION_HISTORICAL_KEYS`, which publishes PingFederate's own retired keys. Switch it on when issuers
    in your federation rotate keys and their holders cannot fetch new marks at once; it reads each issuer's historical
    keys endpoint through the outbound URL policy.
95. **Migrate the federation family to V107 first.** (L01B) The start-up schema check refuses the hosting component on a
    database that is behind, whether or not you use self-signed agents. Run `tools/db-migrate` (or your own Flyway) for
    the `federation` family before the new modules start ([database migrations](../operator/database-migrations.md)).
96. **Expect self-signed agents to work on a database.** (L01B) If you kept an authority on memory only because self-signed
    enrolment failed on a database, you can move it to one now.
97. **Send `federation_jwks` to re-key a self-signed agent.** (L01B) `rotate-key` for a self-signed agent takes the new public
    keys as `federation_jwks`; a body with `hosting_key_ref` is 400 for one, and a body with `federation_jwks` is 400
    for an authority-signed agent, where it used to be ignored. When the answer says `publish_again: true`, the agent
    stops resolving until it publishes again under its new key - on another cluster node, once that node's kept resolve
    responses age out (up to `OIDF_FEDERATION_RESOLUTION_RESOLVE_CACHE_SECONDS`, 60 by default).
98. **Configure the GM PDP and audience.** (REVIEWCFG) Set AUTHZEN_BASE_URL and GM_AUDIENCE or explicit pdpUrl and audience servlet init parameters. The WAR no longer supplies demo defaults. Set the metadata issuer explicitly if required.
99. **Make sure every iOS client sends the bound nonce.** (REVIEWENROL) The enrolment service now refuses an iOS enrolment whose ID
    token does not carry `base64url(SHA-256(UTF-8(challenge + "|" + instance-jkt)))`, where `challenge` is the string
    `POST /enrol/challenge` returned and `instance-jkt` the RFC 7638 thumbprint of `enclave_public_jwk`. Clients built
    on AgentIdentityKit already do. A client of your own that signs the owner in with a random nonce, or none, starts
    failing enrolment with `user_authentication_failed`; see the iOS client contract.
100. **Expect stale sign-ins to be refused at first enrolment.** (REVIEWENROL) An enrolment whose ID token reports an `auth_time`
     older than `UV_MAX_AGE_SECONDS` (default 300) is now `user_verification_required`, however recently the token
     itself was minted. A client that signs the owner in long before it enrols, or reuses a cached token, must sign the
     owner in again (`max_age=0`) just before `POST /enrol`. The challenge is not spent by this refusal.
101. **Use unbound bearer access tokens for GM.** (REVIEWGM) A token containing cnf is refused until proof-of-possession validation is implemented for its binding method.
102. **Keep request bodies within 1 MiB.** (REVIEWHTTP) Requests over the limit return 413. Device-enrolment write routes require POST. Health and JWKS routes require GET. Prefix paths return 404. At capacity, device-enrolment returns 503 with Retry-After; clients should retry.
103. **Make sure every `attestation_bundle_url` is reachable from PingFederate.** (REVIEWJWKS) Before this release a bundle URL that
     had answered once and then stopped answering kept working from the cache indefinitely; now that client's issuance
     fails ten minutes after the last successful fetch. Search the server log for "trust bundle ... could not be
     fetched" or watch `oidf_attester_bundle_stale_total{outcome="refused"}`, and fix the network path or switch the
     client to an inline `attestation_spiffe_bundle`.
104. **Check that your token issuers' and clients' clocks are within a minute of yours.** (REVIEWPINGONE) Any of the JWTs above whose
     `nbf` is more than the allowed skew (60 s, or the attestation skew for the SVID and instance key proof) ahead
     of this server's clock is now refused, where before it was accepted. Tokens without `nbf` are unaffected.
105. **Send bounded enrolment proofs.** (REVIEWPROOF) Set typ to oauth-attestation-instance-proof+jwt. Include iat and exp with a lifetime of 1..300 seconds. The shipped iOS client already sends these fields.
106. **Record or apply the model's ledger rows before the datasource plugin or device-enrolment reads the directory.** (TAIL5)
     An Identity Object Model database whose `idm.schema_migration` does not name `0000-base-schema`,
     `002-backfill-may-attrs` and `006-add-agent-instance-registry` now answers every agent-instance lookup with the
     refusal, as an `ldm` SSF store on it already does, and device-enrolment refuses to start on it. A directory built
     from the model's spec SQL or init scripts has no rows. The refusal says per migration whether to record or apply
     it; follow "The Identity Object Model's ledger" in
     [database-migrations.md](../operator/database-migrations.md#the-identity-object-models-ledger). The plugin
     recovers on its next lookup; restart device-enrolment.
107. **Check the transmitter's clock if you receive device-compliance-change SETs.** (TAIL5) A compliance SET whose
     `event_timestamp` is older than the posture the device records is ignored, so a transmitter whose clock runs behind
     can make the receiver drop real changes. One more than `OIDF_SSF_RECEIVER_MAX_FUTURE_SKEW` (new, 300 s by default)
     ahead is observed at receipt instead. A run of `ssf.receiver.stale_event` from one transmitter means look at its
     clock.

## What is new for integrators

- **The agent registry** (A22): `OIDF_AGENT_REGISTRY_MODE`, `agent_id` on every attestation, and the operator API
  `/federation/attestation/agents/*` on `oidf.admin.agents` and `oidf.admin.agents.read`.
- **Safer attestation sources** (B02A to B11A): CIMD documents per listed client (`OIDF_CIMD_CLIENTS`,
  `OIDF_CIMD_TRUST_BUNDLES`), the attester's cap for external clients and conditional ceilings, listed transit signing
  keys, wallet keys only from `openid_wallet_provider` metadata and wallet revocation by Token Status List, SPIRE
  through the entry reader over mutual TLS, a fail-closed asserted context, and one set of issuer capabilities behind
  the metadata and the enforcement.
- **ABCA draft-11 at the authorization server** (E02 to E06): the challenge header on refusals and `use_dpop_nonce` in
  combined mode, required claims as presence checks, a configurable `typ`, `invalid_client_attestation`, attestations
  without `iss`, metadata that states what is enforced, and opt-in single use.
- **Attestation policy per client** (E07, E08): `attestation_required_trust_marks`, `attestation_min_key_storage` and
  `attestation_min_user_authentication`, each with a server-wide setting.
- **Revocation** (E11 to E14): `OIDF_CLIENT_REVOCATION_MODE` (`off`, `live`, `status_list`, `both`) and a client's
  `attestation_revocation_mode`; the operator API `/federation/attestation/instances/*`; status lists from the
  attester and device enrolment; outbound CAEP on a suspension or revocation (`OIDF_CLIENT_REVOCATION_CAEP`); and
  agent instances over SCIM at `/federation/scim/v2` (`OIDF_SCIM_AGENT_INSTANCES`).
- **Attestation events over SSF** (ATTSSF1 to ATTSSF7): four SETs under
  `urn:idpartners:params:secevent:attestation:1.0:` - `instance-registered`, `attestation-issued`,
  `attestation-refused` and `attester-key-rotated`. A stream hears one only by requesting it, refusals go only to the
  clients in `OIDF_SSF_REFUSAL_RECEIVERS`, and each family has an `OIDF_SSF_*_EVENT_ENABLED` switch.
  `conformance/verify-attestation-events.sh` shows all four on the rig.
- **Refresh-token binding** (E15): `OIDF_ATTESTATION_REFRESH_BINDING` (`on` by default, `strict`, `off` as an accepted
  risk) and a client's `attestation_refresh_binding`.
- **Federation** (L01A, L01B, F0679): Trust Marks under a retired key, the policy engine at every lifecycle step and
  per client, self-signed agents on the authority's database and re-keyed, and a suspended or revoked hosted agent
  refused at once.
- **Fixes from review** (REVIEW*): Grant Management refuses tokens with unverified confirmation bindings and honours its

## Package E08: Minimum key-storage and user-authentication levels at the authorization server

## Package E15: Refresh tokens bound to the client instance key

Owner decision (David, 2026-10-20): the token-endpoint filter does the binding, not PingFederate. It was planned for

## Package L01A: Federation leftovers: Trust Marks under a retired key, the policy engine at every step, and per-client policy settings

L01A, plan item X-L01 (part 1). Closes F-0670, F-0671, F-0672 and F-0673 once the rig run is recorded; U-0670 is
closed (no peer the conformance suite runs publishes historical keys).

The historical keys reader is `HistoricalKeySource` (libs/openid-federation). It reads §8.7.2's "After this time the key
MUST NOT be considered valid" together with §8.7's "Trust Chains will remain verifiable and usable as inputs to trust
decisions after the key expiration, unless the key becomes revoked for a security reason": a key verifies what was
signed before its `exp`, judged by the signed mark's `iat`. Because the signer picks the mark's `iat` and `exp` alike,
the mark must also expire no later than the key (rule `outlives_key`), and a mark without `exp` is never checked with a
retired key. That is what bounds a retired key that leaked without being revoked as compromised: it can sign a
back-dated mark, but none that is still current once the key's own `exp` has passed. Until then such a forgery verifies,
and only the issuer revoking the key as `compromised` stops it sooner; that is why the setting is off by default. Chains
are checked only with their superior's `jwks` (§10.2), and status responses and delegations with current keys.

At the resolve endpoint the policy engine is asked after the subject resolved and before the response is signed; a
response the endpoint kept for up to 60 seconds is served without asking again, so with `resolve` listed one anonymous
caller's permit is served to the next for the same request within that minute.

libs/openid-federation and pf-integration with their 100% METHOD gates. The rig run the specification asks for

## Package REVIEWJWKS: Attestation trust bundles fetched by URL stop verifying after ten minutes without a successful fetch

`RemoteJwksCache` used to serve the last fetched key set on every failed re-fetch, with no limit on its age, so the
300 s TTL only scheduled retries and never stopped a key being accepted (issue #185). It now measures the age from the
last successful fetch, never from the last attempt, and refuses the cached set once that age reaches 600 s, mirroring
the twice-the-maximum-age rule of `RemoteJwks` in rs-validation. A successful fetch replaces the whole set, so a key the
provider withdraws stops verifying at the first refresh after the TTL. The limit is a fixed default, not a setting.
Verified 2026-10-11 by `RemoteJwksCacheTest` over a hand-moved clock: an outage inside the window serves, one past it is
refused and stays refused, a refresh that drops a key stops returning it, and a later success recovers and restarts
the window. Residual risk: while the URL is down, a key withdrawn within the last ten minutes still verifies, and each
lookup past the TTL still re-tries the fetch with no minimum interval between attempts.

## Package TAIL5: The model's ledger for every reader, compliance by event time, and SETs queued under their stream's lock

Built by package TAIL5 (Phase 5, wave 1), 2026-10-09. Nothing changes a table, and `tables` users need do nothing
beyond the clock check above.

PostgreSQL takes the stream row's `FOR SHARE` lock in the fan-out insert before it draws the queued SET's `seq`
(U-0680: tested on PostgreSQL 16 in both orders, and `EXPLAIN VERBOSE` shows the lock as an InitPlan under a one-time
filter with `nextval` in the projection after it), so the `tables` store needed no per-stream counter; the
verification SET's insert and `sets:retry-dead` now take the same lock. The `ldm` store's enqueue takes its stream
entry's share lock, which leaves the entry's content-hash version unchanged; the in-memory store queues under the lock
its status change uses. The race tests ran 50 times in a row on JDK 17 and once on JDK 20; no JDK 21 run was made.

The receiver's ordering by event time is this project's design, not a CAEP or SSF requirement: CAEP 1.0 §2 makes
`event_timestamp` OPTIONAL, and §3.5.1 says that when it is included "its value MUST represent the time at which the
device compliance status changed." A SET without one is observed when it is acted on, as before. Revocations are
unchanged: they only revoke, so their order does not matter.

The 0.7.0 SCHEMA fragment says the plugins that shade platform leave the start-up check out. From this package the
instance-registry datasource keeps `IomLedger` (the model's ledger check) and still leaves `SchemaVerifier` out; the
RAR plugin, the CIBA simulator and `oidf-preflight.jar` are unchanged. `SchemaRefused` is now a top-level class,
`platform.jdbc.SchemaRefused`, no longer nested in `SchemaVerifier`.

The S10f family stays open in idp-scim-service: the `ldm` store needs Identity Object Model classes or attributes for
its stream order, inbox, outbox, replay keys, pause state and optional members, and this repository does not change
the model. F-0511 closes when the model repository ships a step that records what a spec-built database already has.

## Package ATTSSF1: SSF: a signal when a workload agent is first registered

This is the first of the attestation events (feature 206), described in
the SSF module's README. The registers now report a new
`agent_id` on the same hub as a status change (`ClientStatusChangeListener#onRegistered`). They report it after the mint
commits, and only for an `agent_id` they created, so one registration raises one SET on a cluster.
`JdbcAgentRegistry` checks the row it reads back against the ids it generated, rather than trusting the insert's row
count. That way a mint whose insert committed before a retry is still reported once. The event isn't in the default
stream events, so existing streams receive nothing new. New metric: `oidf_ssf_instance_registered_sets_total`. New
events: `ssf.instance_registered.set_emitted` and `ssf.instance_registered.set_suppressed`.

Device instances, which the enrolment service registers in its own process, are covered in ATTSSF2 (#340). There is no
event for a removed instance, because an instance is never deleted; suspension and revocation already raise SETs.

Verified locally with `mvn -B -pl libs/platform,libs/shared-signals,libs/agent-registry,servlets/ssf -am verify` on
JDK 17, with the registry contract run against PostgreSQL 16 in Docker.

## Package ATTSSF2: SSF: a signal when the enrolment service registers a device instance

A new follower (`DeviceInstanceRegistrations`) reads `instance_registered` ledger entries by the time they were written
(`RegistrationLedger#registrationsSince`, implemented by `IomInstanceRegistry` over the existing `jsonb_path_ops` index;
no schema change). Each read goes back 10 minutes behind the newest entry seen, so an entry whose sequence value commits
after a higher one was read is still sent. On the tables store each event's replay key, named for its ledger entry, is
checked in `ssf_logout_replay` in the transaction that appends it to the outbox. That table is the durable cursor: two
nodes send one SET per registration, and a node that restarts sends what was registered while it was down, back one SET
lifetime. The in-memory and `ldm` stores keep their outbox in memory, so there a restart doesn't catch up and can resend
a registration from the last 10 minutes. New metric: `oidf_ssf_instance_registrations_followed_total`.

Verified locally on JDK 17 against PostgreSQL 16 in Docker: `IomInstanceRegistryTest` (the ledger read),
`DeviceInstanceRegistrationsTest` (in-memory store: one SET per registration, a late-committing entry, paging, idle
conditions, read and append failures) and `DeviceInstanceRegistrationsOnPostgresTest` (two nodes and a restart on one
database).

## Package ATTSSF3: SSF: a signal each time an attestation is issued or renewed

The second of the attestation events (feature 206), described in
the SSF module's README. The issuer reports an issuance on the
status-change hub (`ClientStatusChangeListener#onAttestationIssued`) only after it has written the response, so a
refused request, or one refused after the agent was minted, raises nothing. `AgentRegistry#resolve` says whether the
call minted the agent, which is how a first attestation is told from a renewal; an agent minted by a request that was
then refused is marked a renewal on its next attestation. The event isn't in the default stream events, so existing
streams receive nothing new. New metric: `oidf_ssf_attestation_issued_sets_total`. New events:
`ssf.attestation_issued.set_emitted` and `ssf.attestation_issued.set_suppressed`.

Verified locally with `mvn -B -pl libs/platform,libs/shared-signals,libs/agent-registry,servlets/ssf,servlets/attestation-issuer -am verify`
on JDK 17, with the registry contract run against PostgreSQL 16 in Docker.

## Package ATTSSF4: SSF: a signal when the attester's signing key rotates

`AttesterSigningKey` reports a re-read whose signer has a new `kid` on a new platform hub
(`com.pingidentity.ps.oidf.platform.keys.SigningKeyRotations`), and the transmitter appends the event to the outbox with
a replay key named for the key and the new `kid`, checked in `ssf_logout_replay`: two nodes that both pick the rotation
up send one SET. A failed re-read keeps the old signer and reports nothing; a node's first read is not a rotation, so a
rotation every node restarts across before re-reading raises no SET. With the in-memory or `ldm` store each node sends
its own. The event isn't in the default stream events. New metric: `oidf_ssf_attester_key_rotations_total`. New events:
`ssf.attester_key_rotated.set_raised` and `ssf.attester_key_rotated.set_suppressed`.

Verified locally with `mvn -B -pl libs/platform,libs/shared-signals,servlets/attestation-issuer,servlets/ssf -am verify`
on JDK 17, with the two-node test run against PostgreSQL 16 in Docker.

## Package ATTSSF5: SSF: refused attestation requests, for streams an operator flags

The fourth of the attestation events (feature 206), described in
the SSF module's README. The issuer reports a refusal on the
status-change hub (`ClientStatusChangeListener#onAttestationRefused`) after the error response is written, and only for a
4xx: a 5xx is the attester's own failure, not a refusal of the workload. The reason is mapped from the refusal's internal
code, so every refusal site has one without naming it. A refusal names the client only when the request's evidence
matched it, never from the `client_id` the request claims. The flag is checked when a stream is created or updated and
again when a SET is sent, so an owner taken off the list hears nothing more. New metric:
`oidf_ssf_attestation_refused_sets_total`. New events: `ssf.attestation_refused.set_emitted` and
`ssf.attestation_refused.set_suppressed`.

Verified locally with `mvn -B -pl libs/platform,libs/shared-signals,servlets/attestation-issuer,servlets/ssf -am verify`
on JDK 17, against PostgreSQL 16 in Docker.

## Package ATTSSF6: SSF: a switch for each attestation event family

The four families are on by default. None is a default stream event, so a stream hears one only when it asks, and
leaving them on changes nothing for a stream that has not. The switch is for an operator who wants a family sent to
nobody. With the family off, its trigger counts `outcome="disabled"` on its metric (`oidf_ssf_instance_registered_sets_total`,
`oidf_ssf_attestation_issued_sets_total`, `oidf_ssf_attestation_refused_sets_total`,
`oidf_ssf_attester_key_rotations_total`) and its `set_suppressed` event gives reason `disabled`. The emitter also checks the
switch, so a stream whose `events_delivered` named the family before it was switched off hears nothing more. A stream
created or updated while the family is off does not get it in `events_delivered`.

The settings are read at start-up. After a restart that switches instance-registered back on, the device-instance
follower reads back over the SET lifetime on the tables store, as it does after any restart. So a device registered while
the family was off can still be sent.

Verified locally with `mvn -B -pl servlets/ssf -am verify` on JDK 17 against PostgreSQL 16 in Docker, and
`python3 -m unittest discover -s tools/tests` with PyYAML.
